## 1. WCAG 2.2 exact wording (2.5.8, 2.5.5, 2.4.7, 2.4.11, 2.4.13, 1.4.13, 1.4.10)

### Takeaway
All seven criteria are now VERIFIED word for word against the WCAG 2.2 Recommendation dated 12 December 2024. For a desktop tool, 2.5.8 (AA, 24 x 24 CSS px or the 24 px circle spacing test) is the binding size rule. 2.5.5 (44 x 44) is AAA. WCAG treats a slider as one target. 2.4.13 is AAA, but its "2 CSS pixel perimeter, 3:1 between focused and unfocused pixels" test is easy to meet with a solid 2 px outline.

### Cited Findings
- VERIFIED. The document is "W3C Recommendation 12 December 2024". — [WCAG 2.2](https://www.w3.org/TR/WCAG22/)
- VERIFIED. **2.5.8 Target Size (Minimum) (Level AA)**: "The size of the target for pointer inputs is at least 24 by 24 CSS pixels, except when: **Spacing**: Undersized targets (those less than 24 by 24 CSS pixels) are positioned so that if a 24 CSS pixel diameter circle is centered on the bounding box of each, the circles do not intersect another target or the circle for another undersized target; **Equivalent**: The function can be achieved through a different control on the same page that meets this criterion; **Inline**: The target is in a sentence or its size is otherwise constrained by the line-height of non-target text; **User Agent Control**: The size of the target is determined by the user agent and is not modified by the author; **Essential**: A particular presentation of the target is essential or is legally required for the information being conveyed." — [WCAG 2.2 §2.5.8](https://www.w3.org/TR/WCAG22/#target-size-minimum)
- VERIFIED. 2.5.8 Note 1: "Targets that allow for values to be selected spatially based on position within the target are considered one target for the purpose of the success criterion. Examples include sliders, color pickers displaying a gradient of colors, or editable areas where you position the cursor." — [WCAG 2.2 §2.5.8](https://www.w3.org/TR/WCAG22/#target-size-minimum)
- VERIFIED. Understanding 2.5.8 explains the 24 px choice for all pointers: the criterion "is scoped to all pointer input modalities – not just touch, but also mouse, trackpad, stylus and others. Requiring large, touch-optimized minimum sizes would not have been appropriate as a threshold for all pointer inputs. For this reason – after reviewing the average target size of various high-traffic sites – the Working Group settled on the smaller measure of 24 by 24 CSS pixels". It also says: "While not normatively required, authors are encouraged to at least meet the minimum size requirement of the success criterion, regardless of spacing. For important links/controls, consider aiming for the stricter 2.5.5 Target Size (Enhanced)." — [Understanding 2.5.8](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html)
- VERIFIED. **2.5.5 Target Size (Enhanced) (Level AAA)**: "The size of the target for pointer inputs is at least 44 by 44 CSS pixels except when:" Equivalent ("an equivalent link or control on the same page that is at least 44 by 44 CSS pixels"), Inline ("The target is in a sentence or block of text"), User Agent Control, Essential. 2.5.5 has **no spacing exception**. — [WCAG 2.2 §2.5.5](https://www.w3.org/TR/WCAG22/#target-size-enhanced)
- VERIFIED. **2.4.7 Focus Visible (Level AA)**: "Any keyboard operable user interface has a mode of operation where the keyboard focus indicator is visible." — [WCAG 2.2 §2.4.7](https://www.w3.org/TR/WCAG22/#focus-visible)
- VERIFIED. **2.4.11 Focus Not Obscured (Minimum) (Level AA)**: "When a user interface component receives keyboard focus, the component is not entirely hidden due to author-created content." Note 2: "Content opened by the user may obscure the component receiving focus. If the user can reveal the focused component without advancing the keyboard focus, the component with focus is not considered visually hidden due to author-created content." The AAA version 2.4.12 requires that "no part of the component is hidden". — [WCAG 2.2 §2.4.11](https://www.w3.org/TR/WCAG22/#focus-not-obscured-minimum)
- VERIFIED. Understanding 2.4.11: "Typical types of content that can overlap focused items are sticky footers, sticky headers, and non-modal dialogs." It lists technique "C43: Using CSS scroll-padding to un-obscure content" and failure "F110 … due to a sticky footer or header completely hiding focused elements". Content placed by the author, "such as a sticky footer", "must not prevent the item receiving focus from being immediately visible in the viewport". — [Understanding 2.4.11](https://www.w3.org/WAI/WCAG22/Understanding/focus-not-obscured-minimum.html)
- VERIFIED. **2.4.13 Focus Appearance (Level AAA)**: "When the keyboard focus indicator is visible, an area of the focus indicator meets all the following: is at least as large as the area of a 2 CSS pixel thick perimeter of the unfocused component or sub-component, and has a contrast ratio of at least 3:1 between the same pixels in the focused and unfocused states." Exceptions: the indicator "is determined by the user agent and cannot be adjusted by the author", or "The focus indicator and the indicator's background color are not modified by the author." Note 1 says the perimeter "does not include shadow and glow effects outside the component's content, background, or border." — [WCAG 2.2 §2.4.13](https://www.w3.org/TR/WCAG22/#focus-appearance)
- VERIFIED. Understanding 2.4.13: "the simplest way to meet the size requirement is to use a focus indicator which is a solid 2 CSS pixel thick perimeter", and "Offsetting indicators slightly from the focused component … is not required". — [Understanding 2.4.13](https://www.w3.org/WAI/WCAG22/Understanding/focus-appearance.html)
- VERIFIED. **1.4.13 Content on Hover or Focus (Level AA)**: "Where receiving and then removing pointer hover or keyboard focus triggers additional content to become visible and then hidden, the following are true: **Dismissible**: A mechanism is available to dismiss the additional content without moving pointer hover or keyboard focus, unless the additional content communicates an input error or does not obscure or replace other content; **Hoverable**: If pointer hover can trigger the additional content, then the pointer can be moved over the additional content without the additional content disappearing; **Persistent**: The additional content remains visible until the hover or focus trigger is removed, the user dismisses it, or its information is no longer valid." Exception: user-agent-controlled presentation. Note 1 says the HTML `title` tooltip is user-agent content, and Note 2 says "Custom tooltips, sub-menus, and other nonmodal popups that display on hover and focus are examples of additional content covered by this criterion." — [WCAG 2.2 §1.4.13](https://www.w3.org/TR/WCAG22/#content-on-hover-or-focus)
- VERIFIED. Understanding 1.4.13 names Esc as the usual dismiss mechanism: "provide a way for users to dismiss any additional content without the need to move their mouse or keyboard focus, such as pressing the Esc key." — [Understanding 1.4.13](https://www.w3.org/WAI/WCAG22/Understanding/content-on-hover-or-focus.html)
- VERIFIED. **1.4.10 Reflow (Level AA)**: "Content can be presented without loss of information or functionality, and without requiring scrolling in two dimensions for: Vertical scrolling content at a width equivalent to 320 CSS pixels; Horizontal scrolling content at a height equivalent to 256 CSS pixels. Except for parts of the content which require two-dimensional layout for usage or meaning." Note 1: "320 CSS pixels is equivalent to a starting viewport width of 1280 CSS pixels wide at 400% zoom." Note 2 lists exempt content, including "video" and "interfaces where it is necessary to keep toolbars in view while manipulating content." — [WCAG 2.2 §1.4.10](https://www.w3.org/TR/WCAG22/#reflow)
- VERIFIED. Understanding 1.4.10, "Interfaces with persistent toolbars": an example passes when "a photo editing interface presents a fixed-size canvas area, and persistent toolbars, panels and dialogs of controls … The panels and dialogs are resizable and can be made to fit within a 320px wide viewport." — [Understanding 1.4.10](https://www.w3.org/WAI/WCAG22/Understanding/reflow.html)

### Inferences
- The DashLens volume slider counts as **one target** under 2.5.8 Note 1. Its 80 x 16 px box is below 24 px tall, so it passes only through the Spacing exception (no other target inside the 24 px circles) unless its hit box is padded to 24 px. Padding is simpler and safer.
- Reflow still applies to a desktop-only app. A 1280 px window at 400 % zoom gives a 320 px viewport. The video stage, map and timeline are exempt as two-dimensional content, but drawers, dialogs and the settings panel must fit a 320 px width without horizontal scrolling.
- Sticky timeline or footer bars must not fully cover a focused control (2.4.11). `scroll-padding` (C43) is the W3C technique for this.

### Gaps
- None for the wording. The earlier note's "2.5.5 inline exception" text was slightly wrong: 2.5.5 says "in a sentence or block of text", and 2.5.8 says "in a sentence or its size is otherwise constrained by the line-height of non-target text".

## 2. Control heights in desktop design systems (exact numbers)

### Takeaway
VERIFIED across six systems: the desktop default control is **32 px** in Primer, Fluent 2, Spectrum (desktop), Atlassian and Carbon's "small" size. The compact tier is **24 px** (Primer xsmall token, Fluent small, Spectrum 75, Atlassian compact, Carbon xs). The large tier is **40 px**. Primer's "small" is **28 px**, not 24. Carbon is the outlier: its component default for buttons is **48 px** (lg) and for inputs is **40 px** (md). Apple's macOS default control size is 28 x 28 pt with a 20 x 20 pt minimum.

### Inferences
- A **24 / 32 / 40 px** ladder for DashLens matches Fluent 2 (button and input), Spectrum desktop (75/100/200), Atlassian (compact/default) and Primer (xsmall/medium/large). Use 14 px text in the 32 px tier and 12 px in the 24 px tier, as Primer, Fluent and Spectrum do.
- Apple's two macOS hit-region rules conflict. Buttons says 44x44 pt "as a general rule", while Accessibility gives macOS a 28x28 pt default and 20x20 pt minimum. For a pointer-driven web app, the WCAG 24 CSS px floor plus a 28–32 px default sits between them.
- Primer's single-letter example (21.5 px wide) is a direct warning for DashLens's compact icon or text buttons: set `min-width` equal to the height on every square control.

### Gaps
- NOT VERIFIED: Apple's current pixel or point heights for macOS mini, small, regular and large push buttons. The HIG Buttons page lists sizes only for visionOS. Native AppKit metrics would have to come from Xcode or AppKit headers, which were not read.
- GNOME HIG gives no control heights. The libadwaita stylesheet was not read.
- Spectrum's separate per-component button heights were not found as `button-*` tokens. Buttons use the shared `component-height-*` scale, and the S/M/L/XL to 75/100/200/300 mapping is the usual Spectrum CSS convention, but this session did not read it in spectrum-css source. Treat that mapping as NOT VERIFIED.

## 3. Sliders: Carbon, Fluent, Spectrum (Primer has none)

### Takeaway
VERIFIED: all three systems draw a thin track with a thumb much larger than the track. Carbon: 2 px track, 14 px thumb that scales to about 20 px on hover, focus and drag. Fluent medium: 4 px rail, 20 px thumb, 32 px minimum height. Fluent small: 2 px rail, 16 px thumb, 24 px minimum height. Spectrum: current track token 4 px (medium). Primer React has no slider component.

### Inferences
- For the DashLens volume slider: 2–4 px drawn track, 14–16 px thumb growing to about 20 px on hover and drag (Carbon's pattern), and an element box at least 24 px tall (Fluent small `minHeight: 24px`). Together these meet 2.5.8 without the spacing exception.
- The timeline scrubber should follow the same rule: a thin drawn line inside a hit strip of at least 24 px.

### Gaps
- NOT VERIFIED: the current Spectrum 2 handle diameter. Only deprecated handle tokens exist in the package. The Spectrum slider page text gave no pixel values.
- YouTube and Vimeo scrubber dimensions are still unmeasured.

## 4. WAI-ARIA APG toolbar pattern keyboard rules

### Takeaway
VERIFIED. A toolbar is one Tab stop and arrow keys move inside it. Home and End are optional. Wrapping is optional. Focus may return to the last-focused control. A correction to the earlier note: in a **horizontal** toolbar the APG says to *avoid* controls that need Left and Right (such as a horizontal slider). If one is unavoidable, include only one and make it the **last** element.

### Cited Findings
- VERIFIED: "Implement focus management so the keyboard tab sequence includes one stop for the toolbar and arrow keys move focus among the controls in the toolbar." — [APG Toolbar Pattern](https://www.w3.org/WAI/ARIA/apg/patterns/toolbar/)
- VERIFIED: "In horizontal toolbars, Left Arrow and Right Arrow navigate among controls. Up Arrow and Down Arrow can duplicate Left Arrow and Right Arrow, respectively, or can be reserved for operating controls, such as spin buttons that require vertical arrow keys to operate." "In vertical toolbars … Left Arrow and Right Arrow … can be reserved for operating controls, such as horizontal sliders". — [APG Toolbar Pattern](https://www.w3.org/WAI/ARIA/apg/patterns/toolbar/)
- VERIFIED: "Avoid including controls whose operation requires the pair of arrow keys used for toolbar navigation. If unavoidable, include only one such control and make it the last element in the toolbar. For example, in a horizontal toolbar, a textbox could be included as the last element." ## 8. Switch vs checkbox

### Takeaway
VERIFIED. NN/g (2018), Carbon, Primer and Fluent all say a switch must take effect immediately. If a Save or Submit step follows, use a checkbox. GNOME prefers switches to checkboxes in general. Apple says in macOS "don't replace a checkbox with a switch" and to keep switches out of toolbars.

### Cited Findings
- **NN/g** VERIFIED (article dated July 29, 2018): "Toggle switches should take immediate effect and should not require the user to click Save or Submit to apply the new state." "If immediate results are not achievable or seem ill-suited, an alternative (i.e. radio buttons or a single checkbox — see chart above) should be used instead. If you're considering including toggles in long forms where other types of form fields are present, and users will need to click a Submit button for other changes to take effect, don't." The comparison table lists checkboxes as taking effect "After a user clicks a submit button" and toggle switches "Immediately". — [NN/g Toggle-Switch Guidelines](https://www.nngroup.com/articles/toggle-switch-guidelines/)
- **Carbon** VERIFIED: "Toggles are only used for these binary actions that occur immediately after the user "flips the switch"." "Don't use toggles for more than two options". Sizes: default toggle 48 x 24 px with an 18 px handle; small toggle 16 px high. "Use the small toggle when you do not need to specify label or state text … used inline with other components." — [Carbon Toggle usage](https://carbondesignsystem.com/components/toggle/usage/); [Carbon Toggle style](https://carbondesignsystem.com/components/toggle/style/)
- **Primer** VERIFIED: "ToggleSwitches act as instant-save controls for boolean settings, while checkboxes are for selections requiring explicit save actions." - **Fluent 2** VERIFIED: "Toggle buttons are typically used in toolbars. - The rule for DashLens holds: live settings in the drawer use switches, and choices that wait for a "Save" button (the Save-evidence dialog) use checkboxes. In the playback toolbar, use toggle buttons rather than switches (Fluent and Apple).

### Gaps
- None.

## 10. Empty states: Carbon pattern

### Takeaway
VERIFIED (page last updated Aug 11, 2026). An empty state is an optional decorative image, a title written as a positive statement where possible, a body that names the next action, an optional primary action and an optional secondary link. Elements are left-aligned as a block. The empty state replaces the element that would normally show.

### Cited Findings
- VERIFIED anatomy: "Image (optional): A non-interactive image that relates to the situation". "Title: A short and concise explanation. Where possible, write this as a positive statement. In this example, "Start by adding data assets" feels more positive than "You don't have any data assets."" "Body: Explain clearly the next action to populate the space. You may also explain why the space is empty and include the benefit of taking this step." The three ways to point at the action include "Direct the user to the UI element … This has the benefit of teaching the user where elements are and how they will perform tasks in the future." "Secondary call to action (optional): … include it as a link below the copy." — [Carbon Empty states pattern](https://carbondesignsystem.com/patterns/empty-states-pattern/)
- VERIFIED types: "No data empty states" (first use), "User action empty states" (no search results, completion of a process) and "Error management empty states" (permissions, systems, configuration). — [Carbon Empty states pattern](https://carbondesignsystem.com/patterns/empty-states-pattern/)
- VERIFIED layout: "Empty state elements should be left-aligned as a block. The one exception to this rule is an empty state in a small tile." "In situations where there could be multiple empty states showing at once, we recommend using a tertiary button for the call to action." "If space is limited, use just text." — [Carbon Empty states pattern](https://carbondesignsystem.com/patterns/empty-states-pattern/)
- VERIFIED accessibility: "Empty states should replace the element that would ordinarily show. For example, an empty state for a table would replace the table and the column headers and footer should not be present." "As most empty state illustrations are considered decorative, they should be skipped by screen readers." It recommends an empty `alt` over `role="presentation"`. — [Carbon Empty states pattern](https://carbondesignsystem.com/patterns/empty-states-pattern/)
- VERIFIED (related): Fluent 2 Drawer: "If the whole drawer can't be rendered, try an empty state." — [Fluent 2 Drawer usage](https://fluent2.microsoft.design/components/web/react/core/drawer/usage)
