# Make DashLens feel designed, not generated

A web app feels premium when hundreds of small decisions agree with each other: numbers that hold still, a few sizes, radii and greys used everywhere the same way, every state designed, and motion only where it explains something. Decoration has little to do with it. Trust and calm come from the same discipline used under stress. Acute stress measurably shrinks working memory, so the calm interface is the one that asks the user to remember and decide less. It also tells the truth about what it did and what it does not know, and it ends the incident on a clear, lasting "proof saved" moment, because people remember an experience by its worst point and its end. Pro video tools add a shared keyboard grammar (J/K/L, I/O, frame steps, number keys for angles). Dashcam viewers add table stakes that users complain loudly about when they are missing: cameras in sync, telemetry in exports, an honest "no GPS while parked". The uncomfortable finding for DashLens is about its palette. Since 2026, "near-black with a single acid-green or vermilion accent" and "perma-dark page with grey body text" are themselves listed as AI-default fingerprints. The dark theme and the orange `#ffb020` will not make DashLens look designed. Its identity has to come from the footage, the timeline and the evidence workflow, and orange has to become a strict semantic signal rather than a brand colour. The current DESIGN.md already gets the big rules right (one accent, errors on screen, keyboard parity, privacy honesty). What it lacks is the measurable layer underneath: contrast measured in APCA, a closed set of radii, shadows and type sizes, motion tokens, a state checklist, an evidence-grade export, and a written stance on the 2026 slop tells.

## Premium is a closed system of small numbers, and DashLens has drifted

The designers who write about craft all say the same thing. Vercel's interface guidelines open with "Interfaces succeed because of hundreds of choices" ([Vercel](https://vercel.com/design/guidelines)). Linear's 2024 redesign collapsed **98 per-theme colour variables into three inputs** (base, accent, contrast), generated in LCH so every surface, text and icon derives consistently. The team also spent time on label and icon alignment that "isn't something you'll immediately see but rather something that you'll feel after a few minutes of using the app" ([Linear](https://linear.app/now/how-we-redesigned-the-linear-ui)). Refactoring UI warns that ad-hoc `lighten()`/`darken()` calls are "how you end up with 35 slightly different blues" ([Refactoring UI](https://www.refactoringui.com/previews/building-your-color-palette)). What looks like a large design team is a small, closed set of values, applied without exception.

DashLens's `index.html` shows the opposite drift. It uses **ten border-radius values** (2, 4, 5, 6, 7, 8, 9, 10, 12 and 999 px). It has **eight different drop shadows**. It uses seven literal font sizes, although DESIGN.md defines five text roles. It does not set `color-scheme` at all, so native scrollbars and form popups can render in light mode on a dark page, a failure Vercel names explicitly ([Vercel](https://vercel.com/design/guidelines)). No single one of these is visible. Together, they are the "felt" inconsistency Linear describes.

### Numbers that hold still are the cheapest premium signal

For a video and telemetry tool, the most visible amateur tell is a timecode or speed readout whose digits jitter sideways as they change. Vercel's rule is "tabular numbers for comparisons" with `font-variant-numeric: tabular-nums` or a monospace face ([Vercel](https://vercel.com/design/guidelines)). Inter documents `tnum` (tabular figures, "the same width across all weights") and `zero` (slashed zero) as separate features ([Inter](https://rsms.me/inter/)). DashLens already applies tabular figures in several places. The rule should cover **every** changing number: timecode, speed, heading, G values, coordinates, file sizes and timeline ticks. Evidence-grade fields (GPS coordinates, timestamps in the incident summary) should also get a slashed zero, so that 0 and O cannot be confused. Vercel's copy details complete the picture. Put a non-breaking space between a number and its unit (`82&nbsp;km/h`). Use `…` rather than three dots. Format dates and numbers for the locale. Never mix decimal counts within one field ([Vercel](https://vercel.com/design/guidelines)). Applied to telemetry, that means `0.40 g`, never `0.4 g` next to `0.42 g`. Negative G values should use a true minus sign (U+2212) so they align with positive ones in tabular figures.

### Type: a small cluster at 12–14 px, tracked by size, never thin

Premium tools cluster UI text tightly. Vercel's Geist calls Label 14 the "most common text style of all", uses Label 13 with tabular numbers for secondary values, and pairs mono one size smaller than the adjacent sans "as the smaller mono size looks better in that pairing" ([Geist](https://vercel.com/geist/typography)). macOS body text is 13/16 pt, and emphasis comes from weight, not from a new size. Apple's tracking table opens small text (+6/1000 em at 11 pt) and tightens from 13 pt up (−11 at 14 pt, −20 at 16 pt) ([Apple HIG](https://developer.apple.com/design/human-interface-guidelines/typography)). On dark backgrounds, NN/g finds that thin fonts get "swallowed up" and that light-on-dark text reads heavier ([NN/g](https://www.nngroup.com/articles/dark-mode-users-issues/)). NN/g also reports that the advantage of light mode grows as font size falls ([NN/g](https://www.nngroup.com/articles/dark-mode/)). Two rules follow: no weight below 400, and 500 for small labels. On macOS, `-webkit-font-smoothing: antialiased` makes light text on dark render slightly lighter and crisper ([MDN](https://developer.mozilla.org/en-US/docs/Web/CSS/-webkit-font-smoothing)). DashLens does not set it today.

The concrete scale should be 12 px (support and caption), 13 px (body), 14–15 px (panel titles) and 18 px (dialog titles), plus one larger size used only on the drop zone. Apply slight negative tracking from 14 px upward, and use weights 400/500/600 only. Every literal `font-size` in the CSS should map to one of these tokens. The research proposes 11 px all-caps micro-labels, but this report rejects them for two reasons: DESIGN.md's 12 px floor is correct, and all-caps eyebrows are a listed 2026 slop tell (see the AI-slop section).

### Contrast near black needs APCA, and the greys fail it

WCAG 2 overstates contrast near black. The APCA documentation says 4.5:1 "can be functionally unreadable when one of the colors in a pair is near black" and that WCAG 2 "cannot be used for guidance designing 'dark mode'" ([APCA](https://git.apcacontrast.com/documentation/APCA_in_a_Nutshell.html)). Vercel now tells teams to "prefer APCA over WCAG 2" ([Vercel](https://vercel.com/design/guidelines)). APCA asks for **Lc 60** for any text people need to read that is not body copy, Lc 75–90 for body text, Lc 30 for disabled or placeholder text, and Lc 15 as the floor below which dividers are effectively invisible ([APCA](https://git.apcacontrast.com/documentation/APCA_in_a_Nutshell.html)). A re-implementation of APCA on DashLens's tokens gives these values (approximate, ±1–2 Lc):

| Token | WCAG 2 on `--bg` | APCA Lc on `--bg` | Verdict |
|---|---|---|---|
| `--text` #dfe4ea | 15.3:1 | ≈ 90 | Body text: fine |
| `--text2` #c9d0d9 | 12.6:1 | ≈ 77 | Body text: fine |
| `--muted` #9aa4b2 | 7.8:1 | ≈ 52 | Below Lc 60: too dim for 12–13 px secondary text |
| `--dim` #7f8896 | 5.5:1 | ≈ 38 | Disabled and placeholder text only |
| `--acc` #ffb020 | 10.7:1 | ≈ 68 | Icons, playhead, bold labels; not long small text |
| `--line`/`--line2` | 1.2–1.5:1 | ≈ 0 | Invisible as a separator |

Every DashLens text token passes the WCAG rule in DESIGN.md, yet two of them sit below the level APCA sets for readable secondary text. The fix is to move secondary text lighter, to about #aab3bf–#b0b8c4 (verify on apcacontrast.com), and restrict `--dim` to disabled and placeholder text. Hairlines are a second problem. NN/g warns that "thin, gray dividers are easily swallowed up on very dark backgrounds" and recommends separating areas by surface colour ([NN/g](https://www.nngroup.com/articles/dark-mode-users-issues/)). Panels should be separated mainly by a lightness step (bg → panel → panel2, where lighter means closer, as Apple's base/elevated model and NN/g both describe ([Apple HIG](https://developer.apple.com/design/human-interface-guidelines/dark-mode))). Hairlines then become a secondary cue. Radix's 12-step scale gives a ready role map: steps 3/4/5 for component background, hover and selected, 6/7/8 for subtle, default and strong borders, and 11/12 for low- and high-contrast text ([Radix](https://www.radix-ui.com/colors/docs/palette-composition/understanding-the-scale)). DashLens's tokens should be renamed to roles (`--surface-1..3`, `--border-subtle/default/strong`, `--text-primary/secondary/tertiary`, `--accent`, `--accent-hover`, `--accent-subtle`, `--danger`, `--focus`), ideally defined in OKLCH, whose lightness is perceptual ([Evil Martians](https://evilmartians.com/chronicles/oklch-in-css-why-quit-rgb-hsl)).

### Three radii, two elevations, one tint

Vercel's Geist ties radius to elevation: 6 px for base surfaces, 12 px for menus and modals, 16 px for fullscreen. Its rule is that the child radius is no larger than the parent's and concentric with it ([Geist](https://vercel.com/geist/materials); [Vercel](https://vercel.com/design/guidelines)). Geist also warns that "over-elevating is a common source of visual noise" ([Geist](https://vercel.com/geist/materials)). Shadows on dark need **two layers**, ambient plus direct, combined with a semi-transparent border for edge clarity ([Vercel](https://vercel.com/design/guidelines)). For DashLens, this means 4 px for chips and inputs, 8 px for panels and menus, and 12 px for drawers and dialogs. Video tiles get 0–4 px, because large radii crop the picture and read as consumer-grade. The pill shape stays only on toggle chips. All eight shadows collapse into a popover elevation and a modal elevation.

The neutrals need one more decision. DashLens's greys are blue-tinted (`#141820`). Linear reached a "more neutral and timeless appearance" by limiting how much brand chroma enters the neutrals ([Linear](https://linear.app/now/how-we-redesigned-the-linear-ui)). Colour-grading practice holds that the colour surrounding footage biases how the footage's colours are judged, and users object to dark themes with a "distinct blue tint" ([Envato Tuts+](https://photography.tutsplus.com/tutorials/want-better-color-use-neutral-gray-themes-in-adobe-photoshop-and-lightroom--cms-23342); [KDE Discuss](https://discuss.kde.org/t/built-in-gray-theme/45385)). For an incident tool, the colour of a traffic light or a car is evidence. The surround of the video tiles should therefore be near-zero chroma, and the letterbox inside a tile can be true black, so the footage is the most colourful and brightest layer on screen.

## Calm and trust are engineered by subtraction, honesty and the ending

### Polish buys the first-timer's patience, not forgiveness for a broken flow

People rate a page's visual appeal in about **50 ms**, and those ratings match ratings made after longer viewing ([Lindgaard et al. 2006](https://tandfonline.com/doi/abs/10.1080/01449290500330448)). Follow-up work finds that low visual complexity and high prototypicality (looking like what users expect for the category) drive the best first impressions ([Google Research](https://research.google.com/pubs/archive/38315.pdf)). Tractinsky's "what is beautiful is usable" study found that perceived aesthetics shaped usability judgements even after use ([Interacting with Computers](https://academic.oup.com/iwc/article-abstract/13/2/127/898608)). In Stanford's large credibility study, **46.1% of comments cited design or "look"**, more than any other factor ([InternetNews](https://www.internetnews.com/marketing/study-for-site-cred-looks-matter)). The effect has limits. A boundary-conditions study found that users' ratings tracked the manipulated usability instead ([UXPA JUS](https://uxpajournal.org/?p=4392)). Polish raises expectations, and obvious failures then punish harder. The DashLens drop zone should look like a familiar file-open screen: one heading, one primary action, the privacy line, and nothing of the telemetry dashboard until footage exists. The open, find, export path must work on common files before any visual refinement ships.

There is a second, subtler risk in a forensic-adjacent tool: the halo effect can make data look more certain than it is. A smoothed GPS track, interpolated speed or a stylised map can look more precise than the recording. DESIGN.md's "no fake precision" rule should extend to drawing. Show actual sample points or a visible "GPS signal lost" break, not a line bridged across the gap.

### Trust is a claim the user can notice and check

Fogg's prominence-interpretation theory says a credibility signal only works if users notice it ([NN/g](https://www.nngroup.com/articles/prominence-interpretation-theory/)). A privacy line in a footer does nothing. DESIGN.md already requires the in-app privacy line and the map disclosure. The step that makes the claim credible rather than marketing is to make it **verifiable**: a quiet status such as "Processed on this device · map tiles off · 0 network requests", plus a "How to check" link explaining the browser's network tab or offline use. Stanford's guidelines ask sites to make information easy to verify and to avoid errors "of all types… no matter how small they seem" ([Stanford](https://credibility.stanford.edu/guidelines)). One undisclosed request found by a technical user would break the promise for everyone. Dark patterns are common, not hypothetical: Mathur et al. found **1,818 instances on 1,254 of ~11K shopping sites**, including countdown timers that reset on reload ([arXiv](https://arxiv.org/abs/1907.07032v2)). Their total absence is itself a signal. Chayn's trauma-informed principles put "trust and safety over aesthetic or simplicity" and list safety, agency, privacy, accountability and hope ([Promo Cymru](https://promo.cymru/resource/trauma-informed-design-an-introduction-for-non-profits)). These map almost one to one onto what the incident owner needs.

### Stress shrinks working memory, so the interface must remember and decide for the user

A meta-analysis finds that acute stress impairs **working memory and cognitive flexibility** ([Shields et al. 2016](https://pubmed.ncbi.nlm.nih.gov/27371161/)). Anxiety also narrows attention ([PMC](https://pmc.ncbi.nlm.nih.gov/articles/PMC2933078)). Hick's law says decision time grows with the logarithm of the number of choices ([UK DfE](https://accessibility.education.gov.uk/profession-guidance/interaction-design/laws-of-ux)). NN/g's progressive disclosure shows a few key options first, and says to simplify if a design needs three or more levels ([NN/g](https://nngroup.com/articles/progressive-disclosure/)). Shneiderman's rules add easy reversal, which relieves anxiety, and an internal locus of control ([IxDF](https://ixdf.org/literature/article/shneiderman-s-eight-golden-rules-will-help-you-design-better-interfaces)). Together these produce a specific incident path. Propose the strongest event and say why ("Jumped to the strongest impact, 2.4 g at 14:32:11"), and offer "Not this one? See all 3 events". Keep the absolute date, time and speed visible beside the video. Show a persistent "Marked 14:32:08–14:32:38" chip once a range exists, so the user never holds numbers in their head. Never ask "Are you sure?" when nothing is destroyed.

Seeing a collision is emotionally hard. Start **paused a few seconds before the event**, without autoplay at full volume, and let the user choose to play. Reserve red and strong warning styling for real data loss. Red and saturated colours correlate with high arousal across a 128-year literature ([Psychonomic Bulletin & Review](https://link.springer.com/article/10.3758/s13423-024-02615-z)). Routine conditions such as "no rear camera" or "no GPS" are not alarms. Do not justify grey chrome as "calming", though. Specific colour-mood effects replicate poorly: four attempts to replicate red impairing performance failed ([Collabra](https://online.ucpress.edu/collabra/article/6/1/3/113047/Processing-the-Word-Red-and-Intellectual)). Neutral chrome is justified by contrast, convention and letting the video dominate.

Copy carries tone. GOV.UK style says what went wrong and how to fix it, leads with the user's action, and avoids "please", "sorry" and "invalid" ([GOV.UK Design System](https://design-system.service.gov.uk/components/error-message)). Mailchimp keeps voice steady while tone adapts, and "when unsure, keep a straight face" ([Mailchimp](https://styleguide.mailchimp.com/voice-and-tone/)). A strong DashLens error explains and reassures at once: "The last 4 seconds of this clip are damaged, which is common when power is cut in a crash. The rest plays normally." Delight sits at the top of Walter's hierarchy, above function, reliability and usability ([NN/g](https://www.nngroup.com/articles/theory-user-delight/)). Users who imagine something going wrong say they do not want humour then ([UserTesting](https://www.usertesting.com/blog/delight)). DashLens's delight is functional: the event found for you, the cameras synced without asking, a summary sheet ready to email. "Great job!" after exporting crash footage is the wrong register.

### Waiting feels shorter when it is explained, finite and occupied

Maister's propositions hold that uncertain, unexplained and anxious waits feel longer, and that "people want to get started" ([UEN Pressbooks](https://uen.pressbooks.pub/servicesmgt/chapter/chapter-12-the-psychology-of-waiting/)). NN/g's limits are 0.1 s for a response to feel caused by the user, 1 s to keep flow, and 10 s to keep attention ([NN/g](https://www.nngroup.com/articles/response-times-3-important-limits/)). The 400 ms Doherty threshold is a practical target, not a constant ([Kent Beck](https://newsletter.kentbeck.com/p/the-precious-eyeblink?open=false)). Skeleton screens do not reliably feel faster. In Viget's test (n = 136), skeletons felt *slower*, at 2.82 s against 2.41 s for a spinner ([Viget](https://viget.com/articles/a-bone-to-pick-with-skeleton-screens)). DashLens knows its file counts, so it should use determinate, staged progress ("Reading GPS: 9 of 14 clips"), as DESIGN.md already does for the scan. It should also show the first decodable frame before telemetry indexing finishes, so the user can start scrubbing while the rest loads. A long export needs an item that persists after the user moves elsewhere, against Maister's "fear of being forgotten".

### Design the end, because the end is what is remembered

The peak-end rule is among the strongest findings here. In Redelmeier and Kahneman's colonoscopy studies, later judgements were predicted by the worst and final moments, while durations of **4–69 minutes did not significantly matter**. Patients given a milder ending were more likely to return ([Kahneman et al. 1993](https://ius.uzh.ch/dam/jcr:5ae9adc9-61ec-4174-b37c-4b752f36c23b/Kahnemann%20et%20al.%20-%20When%20More%20Pain%20is%20Preferred%20to%20Less%20(1993).pdf)). The incident flow's low point is the first sight of 200 unnamed MP4s. Its end is the export, and that end must not be a toast that vanishes after three seconds. The end should be a **persistent completion state**: "Clip saved: front_rear_2026-11-24_14-32-01.mp4 (30 s). Original files not changed. Summary saved." It should offer "Show in folder" and "Save another angle". The goal-gradient effect shows that effort accelerates as a visible goal nears ([Kivetz et al. 2006](https://business.columbia.edu/sites/default/files-efs/pubfiles/1200/goalgradient.pdf)), which supports a light Find → Review → Save indicator. Starting the user at "Review" because the event was already found is honest progress, not manipulation. A 2025 meta-analysis finds the Zeigarnik memory effect unreliable but the Ovsiankina urge to *resume* interrupted tasks general ([Ghibellini & Meier 2025](https://www.kog.psy.unibe.ch/e48276/e1785865/s41599-025-05000-w1_ger.pdf)). A local-only "Resume where you left off (marked 14:32:08–14:32:38)?" offer, easy to clear, fits both the psychology and the privacy promise. Norman's three levels give the summary: visceral is a calm, edge-to-edge picture; behavioural is instant scrubbing and synced telemetry; reflective is "I handled this well, I have solid proof, and my data stayed private" ([jnd.org](https://jnd.org/emotional-design/)). For the incident owner, the reflective level matters most.

## Borrow the editor's keyboard grammar and the dashcam market's table stakes

### One shared keyboard grammar, shown where it is used

Pro tools converged on one grammar years ago. In Frame.io, I and O set in and out, Shift+I and Shift+O jump to them, arrows step one frame, and Shift+arrow steps ten frames ([Frame.io Help](https://help.frame.io/en/articles/9105337-keyboard-shortcuts)). J/K/L is standard NLE shuttle, where repeat presses speed up, in Premiere, Resolve and Avid's web review tool ([Frame.io](https://support.frame.io/en/articles/7786-player-page-features); [Avid](https://resources.avid.com/SupportFiles/attach/Interplay_Central/IPC_Help/InterplayCentral_Help/UG_Media.16.09.html)). Resolve ships Premiere, FCP and Avid key presets, which shows how much pros value portability ([Storyblocks](https://www.storyblocks.com/resources/blog/davinci-resolve-keyboard-shortcuts)). YouTube, the grammar most owners know, uses J/L as ±10 s jumps and comma/period as frame steps while paused ([YouTube Help](https://support.google.com/youtube/answer/7631406?hl=en)). DashLens should merge the two groups. Use J/K/L as shuttle (1×, 2×, 4×, 8×) with a visible rate badge ("2× ▶"), so YouTube users understand why L did not jump 10 s. Keep comma/period as frame steps beside the arrows, and add Shift+arrow for ±10 frames. Use I/O for the export range, with Shift+I/O to jump to it. Number keys should work in **every** layout, because Resolve users hit angle shortcuts that silently failed in 1×1 view ([Blackmagic Forum](https://forum.blackmagicdesign.com/viewtopic.php?p=420091)). Shortcuts must be page-global outside text inputs; YouTube's "click the player first" focus trap is a known friction point ([YouTube Help](https://support.google.com/youtube/answer/7631406?hl=en)). The pros document shortcuts on separate help pages. DashLens can do better by putting the key in every tooltip ("Play (K)") next to the "?" overlay that DESIGN.md already specifies.

### The timeline is the signature, so make it as precise as Frame.io's

Frame.io V4 sells **frame-accurate seeking with a per-frame hover preview** and comments anchored to a point or a range ([Frame.io blog](https://blog.frame.io/2024/05/28/frame-io-v4-features-player-and-commenting/)). These are precision features, not decoration. DashLens reads local files, so it can build hover thumbnails on demand from a hidden `<video>` and a canvas, caching them like Mux's storyboard sprites ([Mux](https://www.mux.com/docs/guides/create-timeline-hover-previews)). The preview should show the front-camera frame and the wall-clock time. Events and user flags should exist as both a timeline marker and an events-list row, and clicking either should seek. A range flag becomes the export range. Telemetry belongs in **lanes on the same time axis** as the clip rows (speed and G-force under the cameras), so the playhead crosses all of them. This is the NLE audio-waveform idea applied to sensors, and it matches BlackVue's G-sensor graph over its timeline ([BlackVue manual](https://manual.blackvue.com/docs/dr750x-2ch/playing-and-managing-videos/using-your-computer-windows-macos-dr750x-2ch/)). In practice, the playhead's hit area should be at least 24 px wide even though it is drawn 1–2 px thin, which meets the WCAG 2.2 target-size floor ([W3C](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html)). A scrub should keep tracking when the pointer leaves the track while the button is still pressed ([Rauno Freiberg](https://rauno.me/craft/interaction-design)).

### What dashcam users complain about defines the minimum

The market leaders share one layout: video, a map with a live marker, speed and coordinates, a G-sensor graph, and an event-type filter ([BlackVue](https://manual.blackvue.com/docs/dr590x-2ch/playing-and-managing-videos/new-using-your-computer-windows-macos-dr590x-plus-series/); [Dashcam Viewer manual](https://cdn.jjkeller.com/wcsstore/CVCatalogAssetStore/samples/50106/Dashcam-Viewer-Users-Manual-JJ-Keller.pdf)). Users' complaints are about basics: buggy scrubbing and no way to enlarge one camera ([App Store, SentryCam](https://apps.apple.com/us/app/sentrycam/id1468682448)), exports that cannot include sensor data ([SourceForge](https://sourceforge.net/app/dashcam-viewer/mac/)), and timestamps "off by hours" ([TMC](https://teslamotorsclub.com/tmc/threads/teslacam-time-stamp-always-wrong.163874/)). One cause of drift is that per-camera clips for the same minute are not always the same length ([tesla-dashcam](https://pypi.python.org/pypi/tesla-dashcam)). The table below turns these findings into DashLens decisions.

| Pattern from the market | Source | DashLens decision |
|---|---|---|
| Map auto-pans to keep the car centred, with a "keep map fixed" option; route coloured by speed | [Dashcam Viewer manual](https://cdn.jjkeller.com/wcsstore/CVCatalogAssetStore/samples/50106/Dashcam-Viewer-Users-Manual-JJ-Keller.pdf) | Follow/pin toggle; clicking the route seeks; one sequential ramp (not a rainbow) with a legend and numbers |
| Parking recordings carry no GPS | [BlackVue manual](https://manual.blackvue.com/docs/dr750x-2ch/playing-and-managing-videos/using-your-computer-windows-macos-dr750x-2ch/); [heise](https://heise.de/-11112252) | "No GPS while parked: the camera does not record location in parking mode", never a blank map |

### Evidence-grade export is an open gap DashLens can own

Vendor guidance on dashcam evidence is consistent, though it is not law. Courts prefer the original SD-card file, and the master should not be compressed, trimmed or converted ([Nexar](https://www.getnexar.com/blog/why-dash-cam-footage-rejected-as-evidence)). A hash of the original and of each copy should be recorded ([DEV Community](https://dev.to/craig_solomon/chain-of-custody-for-digital-evidence-how-to-prove-your-video-wasnt-faked-56dg)). The package should be the native master plus a playable working copy ([Spot AI](https://www.spot.ai/blog/video-evidence-packages-police-insurers-attorneys)). GPS should be exportable as GPX for independent analysis ([Nexar](https://www.getnexar.com/EN-US/blog/how-to-read-dash-cam-timestamps-gps-data)). Footage should not be "AI-enhanced" ([BlackboxMyCar](https://www.blackboxmycar.com/blogs/news/ai-dash-cam-enhancement-original-footage)). The research found no dashcam viewer that produces a hashed manifest. DESIGN.md's evidence section stops at "export a clip" and "originals stay untouched". The premium version separates **"Export original files"** (byte-for-byte copies) from a clearly labelled **"working copy"** (trimmed, optionally with burned-in telemetry). It computes SHA-256 for every file in the browser with Web Crypto, and writes a manifest into the incident summary: file names, sizes, hashes, camera, recorded start and end times, timezone, export time and DashLens version. The summary page itself should look like a document, not like a dashboard screenshot. Nowhere should DashLens claim legal admissibility.

## Motion should be invisible on the media clock and brief everywhere else

### Frequency decides whether something animates at all

Emil Kowalski's frequency rule is the most useful single idea for a playback tool. Actions used 100+ times a day get **no animation**, tens-of-times actions get reduced animation, occasional surfaces such as drawers and modals get standard motion, and only rare moments get delight. Dashboards "should be crisp and fast" ([Kowalski STANDARDS.md](https://raw.githubusercontent.com/emilkowalski/skills/main/skills/review-animations/STANDARDS.md)). Rauno Freiberg removed motion from his app's core interactions after it "began to feel sluggish" and "suddenly felt like I was moving much faster" ([Rauno Freiberg](https://rauno.me/craft/interaction-design)). In DashLens, play/pause, frame steps, keyboard seeks, number-key tile swaps, the playhead, the map marker and the heading readout must track the media clock 1:1, drawn in the same animation frame as the canvas. That rule exposes a concrete bug in `index.html`. The heading arrow has `transition: transform .3s`. The code already takes the shortest way round at 359°→1°, but the arrow still trails the video by up to 300 ms, and it keeps swinging after a scrub or a frame step has stopped. If smoothing between GPS samples is wanted, it should come from interpolating against the media clock, not from a CSS timer. Other transitions animate `width` (the load and export bars) or use the all-properties shorthand (`transition: .2s` on the toast, `transition: .15s` elsewhere), which Vercel forbids ("Never `transition: all`") ([Vercel](https://raw.githubusercontent.com/vercel-labs/web-interface-guidelines/main/README.md)). Progress bars should animate `transform: scaleX()`, and every transition should list its properties.

### A token set that every source agrees with

Material 3's tokens and Kowalski's tables agree on short durations, ease-out for entrances, and exits faster than entrances (M3 fade is 150 ms in and 75 ms out) ([Material Motion.md](https://raw.githubusercontent.com/material-components/material-components-android/master/docs/theming/Motion.md)). Kowalski says "never use ease-in on UI". M3 uses accelerate curves for exits. Both agree exits should be short, so DashLens can use a fast ease-out for both. Apple recommends starting springs at **100% damping** (no overshoot) and reserving bounce for gestures that carry momentum ([Apple WWDC18](https://developer.apple.com/videos/play/wwdc2018/803/)). No DashLens interaction carries momentum, so it needs no bounce.

| Token | Value | Use in DashLens |
|---|---|---|
| `--dur-0` | 0 ms | Playhead, map marker, heading, frame step, keyboard actions, hover crosshairs on charts |
| `--dur-press` | 120 ms | Button `:active` at `scale(0.97)` ([Kowalski](https://raw.githubusercontent.com/emilkowalski/skills/main/skills/review-animations/STANDARDS.md)) |
| `--dur-fast` | 150 ms | Tooltips, hover colour, toggle thumb |
| `--dur-base` | 200 ms | Menus and popovers (scale from 0.96 at the trigger's origin, never from 0), toast exit |
| `--dur-panel` | 280–320 ms | Settings drawer and dialogs on entry; exits at about 70% of the entry time |
| `--ease-out` | `cubic-bezier(0.23,1,0.32,1)` | All entrances and exits |
| `--ease-drawer` | `cubic-bezier(0.32,0.72,0,1)` | Drawer (the Vaul curve) |
| `--ease-move` | `cubic-bezier(0.2,0,0,1)` | On-screen moves, such as a timeline zoom to an event (M3 Standard) |

Under `prefers-reduced-motion`, DESIGN.md says "no decorative animation". The sources refine this: "fewer, gentler animations, not none" ([Kowalski](https://raw.githubusercontent.com/emilkowalski/skills/main/skills/review-animations/STANDARDS.md)). Keep short opacity fades of 100–150 ms so state changes stay perceptible, and remove only transform-based motion. Tooltips should wait about 700 ms before the first one appears, then show instantly for neighbours within 300 ms (Radix defaults) ([Radix](https://www.radix-ui.com/primitives/docs/components/tooltip)). They should never appear during a drag or scrub. Loading indicators need a **150–300 ms show delay and a 300–500 ms minimum visible time**, so fast local parses never flash a card ([Vercel](https://raw.githubusercontent.com/vercel-labs/web-interface-guidelines/main/README.md)). Interaction to Next Paint should stay at 200 ms or less ([web.dev](https://web.dev/articles/inp)). That means GPS and G-sensor parsing belongs in a Worker, and long clip and event lists should use `content-visibility: auto` with `contain-intrinsic-size`, which rendered about 7× faster in web.dev's demo ([web.dev](https://web.dev/articles/content-visibility)). DashLens should have no UI sounds, which would mix with dashcam audio that may itself be evidence.

### Every state designed is what "a large team" actually means

Scott Hurff's UI Stack names five states for every surface: ideal, empty, loading, partial and error ([Scott Hurff](https://www.scotthurff.com/posts/why-your-user-interface-is-awkward-youre-ignoring-the-ui-stack/)). Vercel adds "No dead ends. Every screen offers a next step or recovery path" and layouts "resilient to user-generated content" ([Vercel](https://vercel.com/design/guidelines)). Templates skip these states, so they are where a small project most visibly outclasses a generated one. DESIGN.md covers errors, scans and missing telemetry. The states it does not yet name are listed below.

| State | DashLens design |
|---|---|
| Drag-over | Whole-window drop target the instant `dragenter` fires; a distinct "can't use these files" look for unsupported types |
| Zero results (distinct from first run) | "No events match 'Hard braking'" plus a Clear-filter action |
| Offline map | Track drawn on a plain background with a note; video and telemetry unaffected |
| Permission denied (File System Access) | Explain the cause and offer the plain file-picker fallback |
| Disabled with reason | "Export needs a marked range", shown beside the control |
| Cancelled or interrupted export | A stated outcome ("Export cancelled; nothing was saved"), not silence |
| Reversible removal (clear files, delete marker) | Undo toast instead of a confirm modal |
| Very many items | Clips grouped by day and trip, counts in headers, keyboard navigation |
| Long file names | Middle ellipsis that keeps the timestamp, camera suffix and extension (`20241012_1432…_F.mp4`), full name in `title` |
| Focus | Distinct selected, focused and hovered looks, including on canvas controls; `outline-offset: 2px` so the ring clears video edges |
| Narrow window | Tiles stack; drawers become full-height sheets |

## DashLens's palette is now an AI fingerprint, so identity must come from the footage

### The tells, and how the target moved in 2026

The 2024–25 core of AI-generated UI appears in every list, including Anthropic's own: purple or indigo gradients, gradient-clipped hero text, blurred aurora blobs and coloured glows, glassmorphism, Inter/Geist type, a centred hero with a "Now in beta" pill above the H1, identical icon-topped cards, stat rows and fake logo strips ([Anthropic](https://claude.com/resources/articles/improving-frontend-design-through-skills); [slop-detect](https://raw.githubusercontent.com/ravidsrk/slop-detect/main/spec/patterns.md)). The open-source slop-detect scorer weights 45 patterns. It gives AI-default fonts a weight of 8, low-contrast body text 7, gradient text 6, and "perma-dark page with grey body text" 4. Its review list adds the same radius and shadow on every card, pulsing status dots, a dark page without `color-scheme`, and the same hover lift and fade-up on everything ([slop-detect](https://raw.githubusercontent.com/ravidsrk/slop-detect/main/spec/patterns.md)). The structural tell is sameness: one section rhythm repeated, and decoration (numbers, labels, borders) that encodes nothing. In an app, this shows up as every panel styled as the same card, every button styled as primary, modals by default, and "No data yet" empty states.

The target moves because of how models work. Anthropic explains that models "converge toward generic, 'on distribution' outputs" and that banning one default shifts the model to the next one: Space Grotesk after Inter ([Anthropic](https://claude.com/resources/articles/improving-frontend-design-through-skills)). The 2025 "fixes" therefore became the 2026 tells. Anthropic's current frontend-design skill lists "a near-black background with a single acid-green or vermilion accent", "tinted near-black", "monospace data labels", all-caps eyebrows, middle-dot meta strings and arrows on buttons as defaults to avoid ([Anthropic SKILL.md](https://raw.githubusercontent.com/anthropics/skills/main/skills/frontend-design/SKILL.md)). Critics describe the 2026 "AI aesthetic" as beige or cream backgrounds, rusty orange accents and large serifs ([Jim Nielsen](https://blog.jim-nielsen.com/2026/ai-aesthetic/), via search summary). Evidence quality is thin. Adrian Krebs's Show HN study, the most-cited measurement, is reported with conflicting numbers (21% versus 22% "heavy"), and its thresholds were tuned on its own sample ([GIGAZINE](https://gigazine.net/gsc_news/en/20260423-design-slop/)). The tells are consensus heuristics, not measured effects. They still matter, because the people evaluating DashLens on GitHub, Hacker News and Reddit use exactly these heuristics.

### Why DashLens is exposed, and why it should keep its dark theme anyway

DashLens matches three 2026 tells at once: near-black with one warm accent, cool-tinted near-black neutrals, and (if allowed to spread) monospace labels. The `index.html` audit adds smaller ones. It has no `color-scheme`. It uses `backdrop-filter: blur(4px)` on the tile labels and the info overlay. It has a pill chip style, and five data colours (`--teal`, `--violet`, `--green` and the red/green/blue G axes) beside the accent. The research is just as clear that the dark theme is right for the product. Apple says an app for immersive media can "use a permanently dark appearance that lets the UI recede" ([Apple HIG](https://developer.apple.com/design/human-interface-guidelines/dark-mode)). A system font stack, which Anthropic also lists as an overused default, is defensible for a single-file app that cannot embed webfonts cheaply. On a Mac it brings SF's optical sizes for free, and it matches the prototypicality that helps first impressions ([Google Research](https://research.google.com/pubs/archive/38315.pdf)). The answer, then, is to keep the palette and make it a system that no generator would produce. Swapping to whatever palette is fashionable next would only move DashLens to the next default, as Anthropic warns.

### Counter-moves that read as authored

The published skills and critics agree on a method. Start from the subject's own vernacular, open with its most characteristic element, "spend your boldness in one place", use real content, and remove every decoration that encodes no information ([Anthropic SKILL.md](https://raw.githubusercontent.com/anthropics/skills/main/skills/frontend-design/SKILL.md)). Pair each ban with a positive alternative, because bans alone do not work ([Latent Space](https://www.latent.space/p/skill-engineering-design)). For DashLens, the vernacular is the dashcam and the edit suite. The one place for boldness is the **timeline**: dense, honest tick marks, event markers that differ in shape as well as colour, hatched and labelled gaps, telemetry lanes, and the amber playhead as the single brightest interactive mark on screen. Everything else stays quiet. Orange becomes semantic: the playhead, the selected event, the primary action, the focus ring, and nothing else. Speed is not orange, data is not orange, and there are no amber glows. The extra data colours need a single audit under DESIGN.md's "one colour, one meaning" rule. `--ax` (#ff6b6b) sits next to `--red` (#ff5d5d, danger), so a G-sensor axis currently looks like an error. The axes should move to a set that does not collide with status colours, and keep their direction words. The blur on tile labels is functional legibility over moving video and can stay. It should not spread to panels or menus, where it becomes glassmorphism.

Monospace stays reserved for values people compare, as DESIGN.md already says. Add an explicit ban on all-caps eyebrows and mono labels. Icons should come from one family drawn on one grid, a 24 px canvas with a 2 px stroke and matched weight ([Lucide guide](https://lucide.dev/guide/design/icon-design-guide)). A few custom glyphs for dashcam concepts (front/rear camera, parking event, impact) should replace generic ones, because stock Lucide everywhere is itself recognised as a vibe-coded signature ([Design Systems Collective](https://www.designsystemscollective.com/is-anyone-else-tired-of-every-tailwind-shadcn-app-looking-the-same-69c545e73114)). Copy should name concrete things ("Drop the folder from your SD card", "Front and rear synced by clock time", brands and formats) in sentence case. It should avoid "seamless", "powerful", "unlock", tricolons and "not just X, it's Y" ([slop-detect](https://github.com/ravidsrk/slop-detect)). Em dashes are the most contested tell, since many human writers use them heavily ([Search Engine Land](https://searchengineland.com/ai-writing-tics-engagement-study-470051)). In UI strings they add nothing a colon or full stop cannot do, so DashLens can drop them without debate. The README's screenshots and any project page should show a real, consented dashcam frame with plates and faces blurred, a real track and a real G trace. Gradient blobs and feature-card grids have no place there.

## Conclusion

What emerges from these five research threads is that "premium", "calm" and "not AI-made" are one property seen from three angles: evidence of an author who made deliberate, consistent decisions about *this* product. A generator produces the most probable interface for "dark video app with orange accent". A designer produces the interface that only a dashcam evidence tool would have. That means a timeline drawn like an edit suite's, numbers that behave like instruments, an export that behaves like a chain-of-custody record, and copy written for someone who has just been hit. The same choices that defeat the slop heuristics also lower the stressed owner's cognitive load and raise their trust, because both audiences read the same thing: intent.

The practical implication is that DashLens's next gains are not visual at all in the usual sense. They come from closing the token sets, measuring contrast with APCA, removing animation from everything tied to the media clock, designing the missing states, and building the hashed evidence package that no competitor offers. A project shipped as one HTML file by a small team cannot out-decorate funded products, but it can out-decide them. Some of the weakest evidence here concerns the slop tells themselves, and that matters too. The fashionable list will move again within a year, while the APCA levels, the peak-end rule and stress research will not. Rules anchored in the domain and in human perception will outlast any rule written only to dodge the current tells.
