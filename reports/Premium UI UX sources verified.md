# Make DashLens look decided, not generated

A web app feels premium, and feels made by a large experienced team, when hundreds of small decisions agree with each other. Numbers hold still. A few sizes, radii, greys and curves are used everywhere the same way. Every state is designed. Motion appears only where it explains cause and effect. Decoration has little to do with it. Trust and calm come from the same discipline applied to a stressed person. Acute stress impairs working memory, so the calm interface is the one that remembers and decides for the user. It makes its claims prominent and checkable. It writes in a plain, almost boring voice. It ends the incident on a lasting "proof saved" state, because people judge an episode by its worst and final moments. Pro video tools supply a documented keyboard grammar (Space/K, J/L shuttle, I/O, frame steps, number keys for angles, a "?" panel). Dashcam viewers supply the floor: cameras in sync, plain trigger names, an honest "no GPS while parked". They also leave one open gap: none of the six products checked mentions hashes or a manifest. NIST, SWGDE and the UK police portal define what an evidence-grade export needs. Since April 2026 the AI-slop tells have been measured and catalogued. DashLens's near-black base with one bright orange accent sits close to a listed AI-default cluster, and so do its 28 middle-dot meta strings and its bright cyan data colour. The fix is not a new palette. Anthropic's own guidance calls these traits "defaults rather than choices", and Impeccable says to keep a dark theme that suits the product but cut the glow. DashLens has to show the choice was made. Verification against primary sources changed several numbers in the earlier report. The APCA levels it relied on were too lenient for 12–13 px text, two motion "standards" turned out to be legacy values, one Frame.io feature was misread, and several user-complaint and colour-grading claims could not be found. All of these are corrected below.

## Premium is a closed set of small numbers, and DashLens still uses thirteen radii

### The large-team feel is consistency you feel before you see it

Vercel's interface guidelines open with "Interfaces succeed because of hundreds of choices" ([Vercel](https://vercel.com/design/guidelines)). Rauno Freiberg describes "hundreds of design decisions made by someone obsessesing [sic] over the tiniest margins so that when they work, no one has to think about" ([Rauno Freiberg](https://rauno.me/craft/interaction-design)). Linear's 2024 redesign replaced **98 theme variables with three inputs** (base colour, accent colour and contrast), generated in LCH. Linear's post calls LCH "perpetually [sic] uniform" for its perceptual lightness. Linear also says its label and icon alignment "isn't something you'll immediately see but rather something that you'll feel after a few minutes of using the app" ([Linear](https://linear.app/now/how-we-redesigned-the-linear-ui)). Its March 2026 refresh went further in the same direction. It dimmed the sidebar "a few notches" so the work area takes precedence, used fewer and smaller icons, and gave borders, which "had quietly proliferated", softer contrast. The principle is "Don't compete for attention you haven't earned" ([Linear 2026](https://linear.app/now/behind-the-latest-design-refresh)). Refactoring UI explains how the opposite happens. Ad-hoc `lighten()`/`darken()` calls are "how you end up with 35 slightly different blues", and a real interface needs "8-10 shades" of grey ([Refactoring UI](https://www.refactoringui.com/previews/building-your-color-palette)).

DashLens's `index.html` shows the drift those sources warn about. A fresh count of the current file finds **13 distinct border-radius values** (2, 4, 5, 6, 7, 8, 9, 10, 11, 12, 14 px, 50% and 999 px). It has **eight different drop shadows** plus one inset ring. Five type tokens exist (`--fs-caption` 12, `--fs-support` 12, `--fs-body` 13, `--fs-section` 15, `--fs-title` 18), yet 26 declarations still use seven literal sizes (12, 13, 14, 15, 16, 17 and 24 px), and `font:` shorthands add 16, 18 and 30 px. The file also does not set `color-scheme`, which Vercel says dark themes need "so that scrollbars and other device UI have proper contrast" ([Vercel](https://vercel.com/design/guidelines)). None of these is visible alone. Together they are the "felt" inconsistency Linear describes.

### Numbers that hold still, and copy that behaves like an instrument

For a video and telemetry tool, the most visible amateur tell is a readout whose digits jitter sideways as they change. Vercel's rule is "Tabular numbers for comparisons. Use font-variant-numeric: tabular-nums or a monospace" ([Vercel](https://vercel.com/design/guidelines)). DashLens already does this on the clock, speed, heading and event times. The rule should cover every changing number: timeline ticks, G values, coordinates, file sizes and counters. Vercel's copy rules give the remaining details. Use a non-breaking space before units (`10&nbsp;MB`, so `82&nbsp;km/h`), the real ellipsis ("Loading…"), numerals for counts, and never mix decimal counts within one field ([Vercel](https://vercel.com/design/guidelines)). Applied to telemetry, that means `0.40 g` beside `0.42 g`, never `0.4 g`. A true minus sign (U+2212) for negative G keeps signed values aligned in tabular figures. That last point is an inference from the tabular rule, not a quoted source.

### Type: a tight cluster at 12–15 px, weights 400 to 600, tracking by size

Geist's typography page shows how premium tools cluster UI text. Label 14 is the "Most common text style of all". Label 13 is "a secondary line next to other labels", with tabular figures "when conveying numbers". Label 13 Mono pairs with Label 14 "as the smaller mono size looks better in that pairing". Label 12 is for "tertiary level text in busy views" ([Geist](https://vercel.com/geist/typography)). Apple's macOS styles are similarly tight. Body is 13/16 pt, Callout 12/15, Title 3 15/20, and emphasis comes from a heavier weight, not a new size ([Apple HIG](https://developer.apple.com/design/human-interface-guidelines/typography)). Apple says to "avoid light font weights" and prefer Regular through Bold. It also says to "Minimize the number of typefaces", because mixing them makes an interface feel "internally inconsistent or poorly designed" ([Apple HIG](https://developer.apple.com/design/human-interface-guidelines/typography)). On dark backgrounds NN/g finds that "Thin fonts can be easily 'swallowed up'" and that light text "tend[s] to appear bolder". The light-mode reading advantage also "increased linearly as the font size was decreased" ([NN/g](https://www.nngroup.com/articles/dark-mode-users-issues/); [NN/g](https://www.nngroup.com/articles/dark-mode/)).

Apple's tracking table needs a corrected reading. Small text is opened (+12 at 10 pt, +6 at 11 pt, 0 at 12 pt) and text is tightened from 13 pt, but only up to 23 pt. Tracking is most negative at **17 pt (−26/1000 em)** and turns positive again from **24 pt**, because SF switches to its Display design there ([Apple HIG](https://developer.apple.com/design/human-interface-guidelines/typography)). The table describes SF's own spacing. DashLens embeds IBM Plex Sans (400–600) and IBM Plex Mono (400/500/600), so it should copy only the direction: zero tracking at 12 px, slight negative tracking from 13 to about 18 px, none on large display numbers. The token set DashLens already has (12, 13, 15, 18) is the right scale. The job is to replace every literal size with a token and to add one named `--fs-readout` for the 30 px speed value and the 24 px drop-zone heading, so that every size in the file is a decision.

### APCA contrast near black is stricter than the earlier report said

WCAG 2 overstates contrast for dark colours "to the point that 4.5:1 can be functionally unreadable when one of the colors in a pair is near black", so "WCAG 2.x contrast cannot be used for guidance designing 'dark mode'" ([APCA](https://git.apcacontrast.com/documentation/APCA_in_a_Nutshell.html)). Vercel says "Prefer APCA over WCAG 2" ([Vercel](https://vercel.com/design/guidelines)). Radix guarantees its text steps 11 and 12 at **Lc 60 and Lc 90** on its step-2 background ([Radix](https://www.radix-ui.com/colors/docs/palette-composition/understanding-the-scale)). The exact APCA levels matter here. **Lc 90** is preferred for body text and for "non-body text with a font no smaller than 12px/400". **Lc 75** is the body minimum and allows non-body text from 15 px/400. **Lc 60** is for "text you want people to read", but only from 24 px/400, 18 px/600 or 16 px/700. **Lc 45** is for headlines of 36 px, or 24 px bold, and for fine-detail outline icons. **Lc 30** is the floor for placeholder and disabled text. **Lc 15** is the floor for solid non-text at least 5 px thick, and fine details such as 1 px lines "have a higher minimum" ([APCA](https://git.apcacontrast.com/documentation/APCA_in_a_Nutshell.html)). The status needs care too. APCA calls itself "the candidate contrast method for the future WCAG 3", but the W3C's WCAG 3.0 draft of 10 September 2026 says "The contrast algorithm used in WCAG 3 is yet to be determined" and does not name APCA ([W3C](https://www.w3.org/TR/wcag-3.0/)). WCAG 2.2 AA stays the compliance baseline, and APCA is the design tool.

The verification pass recomputed every DashLens token with the official `apca-w3` 0.1.9 package. The results match the earlier hand calculation within 0.5 Lc. These are APCA Bronze ("simple mode") readings, without the font lookup tables ([apca-w3](https://www.npmjs.com/package/apca-w3)).

| Token (uses in `index.html`) | WCAG 2 on `--bg` #0a0c0f | APCA Lc on `--bg` / `--panel` | What APCA allows it to do |
|---|---|---|---|
| `--text` #dfe4ea (23) | 15.3:1 | 89.8 / 88.9 | Just under Lc 90; lift slightly for 12 px values |
| `--text2` #c9d0d9 (12) | 12.6:1 | 77.4 / 76.5 | Lc 75 band: secondary text that must be read |
| `--muted` #9aa4b2 (35) | 7.8:1 | 52.3 / 51.4 | Lc 45 band: large or bold text and hints only |
| `--dim` #7f8896 (4) | 5.5:1 | 38.0 / 37.1 | Lc 30 band: placeholder and disabled only |
| `--acc` #ffb020 (27) | 10.7:1 | 68.5 / 67.6 | Icons, playhead, short bold labels |
| `--red` #ff5d5d (3) | 6.5:1 | 45.7 / 44.8 | Shapes and large text, not small error copy |
| `--line` #20262f, `--line2` #2c3340 (44) | 1.2–1.5:1 | 0 / 0 | Below APCA's measurable floor |
| `--line3` #3d4656 (3) | 2.1:1 | 10.2 / 9.3 | Still below Lc 15 |

Every text token passes the 4.5:1 rule in DESIGN.md, and that is exactly the problem APCA describes. The most-used grey, `--muted`, sits at Lc 52 and is used 35 times, mostly for 12–13 px labels. That is below even Radix's low-contrast floor of Lc 60. The corrected rule is three readable steps plus one disabled step. Primary text should reach at least Lc 90 on the lightest panel: the neutral threshold on #141820 is about #e6e6e6, so `--text` should move up a few steps, for example to about #e8ebef (verify with apca-w3). Secondary text should be at least Lc 75, which `--text2` already meets. It should become the floor for anything the stressed owner must read: error text, the incident summary and settings explanations. A tertiary step at Lc 60 or more (neutral threshold about #b3b3b3) is acceptable only for short, non-critical labels at weight 500 or more, following Radix's step 11. `--dim` stays for disabled and placeholder text. The threshold greys computed for #141820 give a quick reference: **Lc 15 #555555, Lc 30 #797979, Lc 45 #979797, Lc 60 #b3b3b3, Lc 75 #cdcdcd, Lc 90 #e6e6e6**.

### Separate surfaces by lightness; keep hairlines as faint texture

Material's dark theme recommends **#121212** and says to "Use dark grey – rather than black – to express elevation". Its reason is that "it's easier to see shadows on grey". Its text sits at 87, 60 and 38% white for high, medium and disabled emphasis ([Material Design 2](https://m2.material.io/design/color/dark-theme.html)). Material 3 replaced elevation overlays with tonal surface containers. In Google's colour library the dark tones are surface 6, container-lowest 4, low 10, container 12, high 17 and highest 22. Converted to neutral greys, that is about #0e0e0e, #131313, #1b1b1b, #1f1f1f, #2a2a2a and #353535, roughly 4–5 L\* apart ([Material 3](https://m3.material.io/styles/color/roles); [material-color-utilities](https://github.com/material-foundation/material-color-utilities/blob/main/typescript/dynamiccolor/color_spec_2021.ts)). Apple's base and elevated sets work the same way, with "elevated colors… brighter, making foreground interfaces appear to advance" ([Apple HIG](https://developer.apple.com/design/human-interface-guidelines/dark-mode)). NN/g adds that "Thin, gray dividers are easily swallowed up on very dark backgrounds" and recommends "slight color differentiation" instead ([NN/g](https://www.nngroup.com/articles/dark-mode-users-issues/)). DashLens's three surfaces (#0a0c0f, #141820, #1a1f28) fit the lower M3 steps. It needs one or two more steps for raised menus and the selected state, and its 44 uses of Lc 0 hairlines should become texture, not structure. Any line that carries meaning, such as a focus ring, the selected-tile outline or the timeline track edge, needs at least about #555555 on #171717, or the accent. Geist adds two craft details that apply to the tile grid. "Draw each border once", because overlapping alpha borders make intersections stand out. "Keep material shadows translucent", because "Opaque shadows leave a gray halo" ([Geist Colors](https://vercel.com/geist/colors)).

### Three radii, two elevations, and low chroma applied the same way everywhere

Geist ties radius to elevation: **6 px** for base and small surfaces and tooltips, **12 px** for medium and large surfaces, menus and modals, and **16 px** for fullscreen. It also says to "Favor the lowest elevation that still reads as elevated", because "over-elevating is a common source of visual noise". It warns that "shadow contrast on dark backgrounds is weaker than on light" and that elevation should not rely on shadow alone ([Geist Materials](https://vercel.com/geist/materials)). Vercel's rules complete the set: "Child radius ≤ parent radius & concentric", "Layered shadows… at least two layers" and "semi-transparent borders improve edge clarity" ([Vercel](https://vercel.com/design/guidelines)). This report changes the earlier 4/8/12 proposal to Geist's sourced **6/12/16**. Chips, inputs, buttons, tooltips and video tiles get 6 px. Menus, popovers, dialogs and the settings drawer get 12 px. Only a fullscreen overlay gets 16 px, and only the switch and round dots stay fully rounded. The eight shadows collapse into two layered elevations, popover and modal.

The neutrals need one decision, not a fashionable tint. Linear's 2024 post moved to a "more neutral and timeless appearance" by limiting the blue in its calculations. Its 2026 post moved from "a cool, blue-ish hue" towards "a warmer gray that still feels crisp, but less saturated", with the warning "Go too warm, though, and the interface risks looking muddy" ([Linear](https://linear.app/now/how-we-redesigned-the-linear-ui); [Linear 2026](https://linear.app/now/behind-the-latest-design-refresh)). Either tint is defensible. What matters is low chroma, applied the same way across every grey step. The colour-grading argument for neutral video surrounds is weaker than the earlier report said. Frame.io's 18% grey advice is about painting the grading suite's **walls**, not the software ([Frame.io Workflow Guide](https://workflow.frame.io/guide/color-correction-suites)). ITU-R BT.2035 specifies a **D65-neutral background at about 10% of reference white** behind a reference display ([ITU-R BT.2035](https://www.itu.int/dms_pubrec/itu-r/rec/bt/R-REC-BT.2035-0-201307-I!!PDF-E.pdf)). Applying that to app chrome is an analogy, not a rule. It still supports keeping the area directly around the video near-neutral, so that the colour of a traffic light or a car, which may be evidence, is judged against nothing tinted. Material's dark-theme page gives the reason to keep the accent light: "Saturated colors also produce optical vibrations against a dark background", so dark themes use lighter "200" tones ([Material Design 2](https://m2.material.io/design/color/dark-theme.html)). `#ffb020` is already a light, warm tone, which suits that rule.

## Calm and trust come from fewer decisions, checkable claims and a designed ending

### Polish wins the first 50 ms, then real usability takes over

People rate visual appeal within 50 ms. Lindgaard's third study found those ratings "highly correlated" with ratings made after **500 ms** of exposure, not after long viewing, as the earlier report implied ([Lindgaard et al. 2006](https://api.openalex.org/works?filter=doi:10.1080/01449290500330448)). Low visual complexity and high prototypicality drive those first impressions even at 17 ms ([Tuch et al., Google Research](https://research.google.com/pubs/archive/38315.pdf)). Tractinsky's ATM study found that aesthetics "affected the post-use perceptions of both aesthetics and usability, whereas the degree of actual usability had no such effect" ([Tractinsky et al. 2000](https://api.openalex.org/works?filter=doi:10.1016/S0953-5438(00)00031-X)). Later controlled work reverses the direction once people do real tasks. In Tuch et al. (2012, N = 80), four versions of a shop varied beauty and usability. Beauty "did not affect how users perceived the usability", while "poor usability lead to frustration" and lowered beauty ratings ([Google Research blog](https://www.research.google/blog/is-beautiful-usable-what-is-the-influence-of-beauty-and-usability-on-reactions-to-a-product/)). Hamborg et al. (N = 88) found the same: usability affected perceived beauty, not the other way round ([Hamborg et al. 2014](https://doi.org/10.1155/2014/946239)). For DashLens, polish buys the first-timer's patience, but a broken export or a hidden event will make the whole app look worse. The drop zone should look like a familiar file-open screen, and the open, find, export path must work before visual refinement ships.

A finding that the earlier report undersold supports investing in clarity where the task is hardest. Reppa and McDougall found that appealing icons "were found more quickly", "especially under duress", with "no benefits when the task was made easier" ([Reppa & McDougall 2015](https://pmc.ncbi.nlm.nih.gov/articles/PMC4577531/)). Moshagen et al., as they report it, found aesthetic appeal improved performance only on low-usability sites. Perrig et al. (N = 281) found a positive effect on correct answers and cite a meta-analysis with a **small effect, g = 0.12** ([Perrig et al. 2023](https://pmc.ncbi.nlm.nih.gov/articles/PMC10306164/)). That meta-analysis was not read directly. The incident flow, where the stressed owner must find one marker among hundreds of clips, is where legible, well-drawn event markers pay most. There is also a risk specific to a forensic-adjacent tool. Polish can make data look more certain than it is. A smoothed GPS line or a speed interpolated across a gap looks precise. DESIGN.md's "no fake precision" rule should extend to drawing: plot recorded samples and break the line where GPS was lost.

### Trust signals work only when they are prominent and checkable

The Stanford study had **2,684 participants** who wrote **2,440 comments**. "Design look" appeared in **46.1% of the comments**, a share of comments, not of people, and in 54.6% for finance sites ([Fogg et al. 2002](https://advocacy.consumerreports.org/wp-content/uploads/2013/05/stanfordPTL.pdf)). The same report found that people "almost never referred to a site's privacy policy": **privacy policies appeared in under 1% of comments**. The often-quoted line "To look good is to be good" is not in the report; it comes from press coverage. Experts behaved differently. Only 16.4% of finance experts' comments and 7.6% of health experts' comments mentioned design look, and experts "were more concerned about the quality of a site's information" ([Stanford et al. 2002](https://advocacy.consumerreports.org/wp-content/uploads/2013/05/expert-vs-online-consumers.pdf)). Prominence-interpretation theory explains why: a signal counts only if users notice it ([NN/g](https://www.nngroup.com/articles/prominence-interpretation-theory/)). DashLens already shows "Nothing is uploaded and nothing is tracked" on the first screen and in Settings, as DESIGN.md requires. The next step is to make the claim checkable. A quiet live status such as "Processed on this device · map tiles off · 0 network requests" would do it, with a short "How to check" note pointing to the browser's network panel. The Stanford guidelines start with "Make it easy to verify the accuracy of the information" and end with "Avoid errors of all types, no matter how small they seem" ([Stanford](https://credibility.stanford.edu/guidelines/)). For the insurer or police officer who reads the export, verifiable facts beat styling.

Dark patterns are measured, not hypothetical. Mathur et al. found **1,818 instances on 1,254 of about 11K shopping sites (11.1%)**, a lower bound. More popular sites were more likely to use them ([Mathur et al. 2019](https://arxiv.org/pdf/1907.07032)). Their total absence in DashLens is itself a signal. Chayn's trauma-informed work gives the incident owner's priorities. Hera Hussain's 2021 article says Chayn will "prioritise trust and safety over aesthetic or simplicity", and that trust comes from being "consistent and predictable" ([UX Magazine](https://uxmag.com/articles/trauma-informed-design-understanding-trauma-and-healing)). The later eight-principle set names "videos" among the personal information that "must be kept secure and not disclosed, unless the survivor decides to do so". It also says a service will trigger someone at some point, so it needs "a plan to mitigate the impact" ([Promo Cymru](https://promo.cymru/resource/trauma-informed-design-an-introduction-for-non-profits)).

### Stress shrinks working memory, so the interface must hold the numbers

A meta-analysis found that acute stress "impaired working memory and cognitive flexibility", with "more reactive processing of salient stimuli" ([Shields et al. 2016](https://pubmed.ncbi.nlm.nih.gov/27371161/)). Nielsen's progressive disclosure says to show "only a few of the most important options" first, and warns that designs needing "3 or more levels" should be simplified ([NN/g](https://www.nngroup.com/articles/progressive-disclosure/)). The incident path that follows is specific. Propose the strongest event and say why ("Jumped to the strongest impact, 2.4 g at 14:32:11"), with "Not this one? See all 3 events" beside it. Keep the absolute date, time and speed visible next to the video. Once a range is marked, show a persistent "Marked 14:32:08–14:32:38" chip, so the user never holds numbers in their head. Never ask "Are you sure?" when nothing is destroyed. Seeing a collision is hard, so open **paused a few seconds before the event**, with audio off or low, and let the user press play. That is the "plan to mitigate" that Chayn asks for.

Colour psychology supports less than designers usually claim. The largest review covers **132 articles, 42,266 participants and 64 countries** and was published in 2025. It links red with "high arousal positive and negative emotions", yellow and orange with "positive, high arousal" ones, blue and green with positive low arousal, and grey with **negative**, low arousal ones. The authors note that these are associations, and "it remains to be seen" whether they change felt emotion ([Jonauskaite & Mohr 2025](https://link.springer.com/article/10.3758/s13423-024-02615-z)). Four replications of the "red impairs performance" effect failed ([Gnambs et al. 2020](https://doi.org/10.1525/collabra.277)). A meta-analysis found "no evidential value" after correcting for publication bias ([Psychon Bull Rev 2020](https://doi.org/10.3758/s13423-020-01772-1)). Neutral chrome is justified by contrast and by letting the footage dominate, not by a claim that grey calms people. Red should still be reserved for real problems, because it is the one colour whose meaning ("stop, danger") users bring with them. DashLens currently draws **braking in #ff5d5d**, the same red it uses for danger and for event markers on the timeline. A firm stop then looks like an error, which breaks DESIGN.md's "one colour, one meaning" rule.

### Write the incident flow to be boring

The UK government's writing guide gives the clearest rule for this user: "Avoid things like humorous error messages. People often use government services for serious things or when under stress", and "If people do not notice your copy, you're probably doing it right. Aim to be boring" ([GOV.UK Service Manual](https://www.gov.uk/service-manual/design/writing-for-user-interfaces)). Its error-message guidance says to "explain what went wrong and how to fix it". It bans jargon, "please", "sorry", "valid"/"invalid" and "oops", and requires "Different errors need different messages" ([GOV.UK Design System](https://design-system.service.gov.uk/components/error-message/)). It also advises against negative contractions such as "can't", which "some users… misread… as the opposite". Atlassian's tone guidance agrees. When a person feels "overwhelmed, unsure, hesitant, stressed", be more practical, and save the "wink" for when they feel "successful, joy, proud, relief". Even then, "Delight means little flourishes, not humor" ([Atlassian](https://atlassian.design/foundations/content/voice-tone)). Mailchimp's rule is "If you're unsure, keep a straight face" ([Mailchimp](https://styleguide.mailchimp.com/voice-and-tone/)). NN/g's theory of delight puts it in function: "deep delight can only be achieved in functional, reliable, and usable interfaces" ([NN/g](https://www.nngroup.com/articles/theory-user-delight/)). A strong DashLens error explains and reassures at once: "The last 4 seconds of this clip are damaged. This often happens when power is cut in a crash. The rest of the clip plays normally." The functional delight is the event found for the user, the cameras synced without asking, and a summary ready to send.

### Explained, counted and cancellable waits feel shorter

Nielsen's limits are **0.1 s** to feel instantaneous, **1 s** to keep flow and **10 s** to keep attention. "Anything slower than 10 seconds needs a percent-done indicator as well as a clearly signposted way for the user to interrupt" ([NN/g](https://www.nngroup.com/articles/response-times-3-important-limits/)). NN/g's progress-indicator rules add the detail DashLens needs. Show an indicator for anything over about 1 s. Use a spinner only for 2–10 s. Use percent-done for 10 s or more, or under 10 s when "processing a series of documents", with text such as "Updating address 3 of 50". Start the bar slowly, never let it race and then hang at the end, give "a general time estimate" and offer a way to stop ([NN/g](https://www.nngroup.com/articles/progress-indicators/)). The skeleton-screen advice in the earlier report is withdrawn. NN/g says skeletons are for full-page loads only, and for "download, upload, convert a file" a progress bar should be shown instead ([NN/g](https://www.nngroup.com/articles/skeleton-screens/)). The one peer-reviewed study it cites "cannot show any significant differences" ([Mejtoft et al. 2018](https://api.openalex.org/works?filter=doi:10.1145/3232078.3232086)). Maister's eight propositions turn into DashLens rules ([Maister](https://davidmaister.com/articles/the-psychology-of-waiting-lines/)). Explained waits feel shorter, so name the stage ("Reading GPS: 9 of 14 clips"). Finite waits feel shorter, so show counts. Occupied waits feel shorter, so let the user scrub the first decoded clip while indexing continues. Anxiety comes from a "fear of 'being forgotten'", so a long export keeps a visible status until it finishes. His "S = P – E" (satisfaction is perception minus expectation) argues for cautious estimates that the app then beats. Adding fake "analysing…" delays to look thorough, which Laws of UX suggests without a source, would be dishonest in a tool that promises honesty.

### Design the end, because the end is what is remembered

In Kahneman's cold-water study, a majority chose to repeat the longer trial because its end was milder. Evaluations were "dominated by the discomfort at the worst and at the final moments" ([Kahneman et al. 1993](https://doi.org/10.1111/j.1467-9280.1993.tb00589.x)). In colonoscopy (n = 154) and lithotripsy (n = 133), total pain tracked the peak and the last 3 minutes, and "lengthy procedures were not remembered as particularly aversive" ([Redelmeier & Kahneman 1996](https://pubmed.ncbi.nlm.nih.gov/8857625/)). The behavioural effect is real but modest. In a randomised trial (n = 682), patients given a gentler ending were only "slightly higher" in returning for a repeat procedure, with an **odds ratio of 1.41** ([Redelmeier et al. 2003](https://pubmed.ncbi.nlm.nih.gov/12855328/)). A good ending is worth building, but it will not rescue a bad flow. The incident's low point is the first sight of hundreds of unnamed MP4 files. Its end is the export, and the end must not be a toast that vanishes. It should be a persistent completion state: "Clip saved: front_rear_2026-11-24_14-32-01 (30 s). Original files not changed. Summary and hash list saved." It should offer "Show in folder" and "Save another angle". The goal-gradient effect, in which a 12-stamp card with two bonus stamps is completed faster than a plain 10-stamp card, supports a light Find → Review → Save indicator that honestly starts at "Review" when the event was already found ([Kivetz et al. 2006](https://business.columbia.edu/sites/default/files-efs/pubfiles/1200/goalgradient.pdf)). A 2025 meta-analysis found no memory advantage for unfinished tasks (ratio 0.99 over 38 publications). It did find that interrupted tasks are resumed about **67%** of the time ([Ghibellini & Meier 2025](https://www.nature.com/articles/s41599-025-05000-w)). That supports a local, easily cleared "Resume where you left off (marked 14:32:08–14:32:38)?" offer, and argues against nagging "unfinished" badges. NN/g's pillars of delight use Norman's three levels: visceral, behavioural and reflective ([NN/g](https://www.nngroup.com/articles/pillars-user-delight/)). For the incident owner, the reflective level matters most: "I handled this well, I have solid proof, and my data stayed private."

## Borrow the editor's keyboard grammar; the dashcam market sets the floor; evidence is the open gap

### One documented grammar, shown where it is used

Frame.io's current shortcut list is the cleanest model. Space or K plays and pauses. J and L play at "multiple speeds", and Shift+J/L at "incremental" speeds. The arrows step one frame and Shift+arrow ten frames. I and O mark in and out, Shift+I/O go to them, R marks a range and C adds a comment. A "?" panel lists everything, and shortcuts can be remapped ([Frame.io Help](https://help.frame.io/en/articles/9105337-keyboard-shortcuts)). Its player shows "A visual signifier of your current speed… each time you use a shortcut" ([Frame.io Help](https://support.frame.io/en/articles/7786-player-page-features)). Final Cut Pro documents the shuttle precisely. J/K/L play at "up to 32x", each extra press doubles the speed, and holding K while pressing J or L steps one frame. Command-plus and minus zoom, Shift-Z fits, and keys 1–9 switch multicam angles ([Apple FCP guide](https://support.apple.com/guide/final-cut-pro/play-media-ver90ba4ef0/mac); [Apple FCP shortcuts](https://support.apple.com/guide/final-cut-pro/ver90ba5929/mac)). Blackmagic's own shortcut PDF (actually the Resolve 11 guide) has the same J/K/L, I/O, Shift+I/O and Shift+Z ([Blackmagic](https://documents.blackmagicdesign.com/UserManuals/DaVinci-Resolve-15-Keyboard-Shortcuts.pdf)). YouTube, the grammar most owners know, differs. J/L jump ±10 s, comma and period step frames while paused, Shift+? lists shortcuts, and button tooltips show the key ("Full screen (f)"). The new YouTube player also needs a click on the player before keys work ([YouTube Help](https://support.google.com/youtube/answer/7631406?hl=en)).

DashLens's current handler already covers much of this. Space/K play, J/L step through rates from 0.25× to 16×, arrows and comma/period step frames, I/O set the range, E and Shift+E jump between events, 0–9 pick cameras, "?" opens help, and shortcuts work page-wide outside text inputs. Four gaps remain against the documented grammar. First, there is no on-video speed badge, although Frame.io shows one and YouTube users will otherwise expect L to jump 10 s. Second, Shift+I/O do not jump to the marks. Third, Shift+arrow means ±5 s, where pro tools mean ±10 frames. That is a defensible dashcam choice, but it must be stated in the "?" list and in tooltips. Fourth, there is no keyboard timeline zoom. In a browser, Ctrl/Cmd-plus belongs to page zoom, so Shift+Z for "fit" plus bare = and − is the safer mapping. J cannot play in reverse with HTML video in most browsers, so DashLens should say "slower", not "reverse", where it shows J. Frame.io's focus handling is worth copying for markers and notes: "When you submit a comment, focus immediately shifts back to the player", and typing pauses playback ([Frame.io blog](https://blog.frame.io/2024/05/28/frame-io-v4-features-player-and-commenting/)).

### The timeline is the signature, so make it as precise as Frame.io's

Frame.io V4 sells "frame-accurate seeking… hovering over the timeline and seeing a preview of each frame" ([Frame.io blog](https://blog.frame.io/2024/05/28/frame-io-v4-features-player-and-commenting/)). The earlier report also said V4 anchors comments to ranges. That was wrong. V4's "anchored comments" are pinned to "any point or pixel" in the frame, layered on top of time-stamped comments ([Frame.io V4 beta](https://blog.frame.io/2024/04/09/frame-io-version-4-beta-is-here/)). Range comments are documented in the legacy player (I/O then C), and V4 has "Mark range: R". The corrected reading suggests a better feature for DashLens: a **pin on the frame** ("other vehicle", "traffic light") that is carried into the incident summary's still image. A hover preview should show the front-camera frame and the wall-clock time. Telemetry belongs in lanes on the same time axis as the clip rows, so the playhead crosses video, speed and G together. Dashcam Viewer lets users "click in a graph to jump to that exact moment" ([Dashcam Viewer](https://dashcamviewer.com/)), and BlackVue shows G-sensor data "in the line graph" ([BlackVue](https://manual.blackvue.com/docs/dr750x-2ch/playing-and-managing-videos/using-your-computer-windows-macos-dr750x-2ch/)). Vercel's rule for thin targets applies to the 1–2 px playhead: "if the visual target is < 24px, expand its hit target to ≥ 24px" ([Vercel](https://vercel.com/design/guidelines)). Rauno's slider rule, that a drag "does not cancel when moving away from the slider and still pressing down", is already met through `setPointerCapture` on the timeline ([Rauno Freiberg](https://rauno.me/craft/interaction-design)).

### Evidence-grade export is unclaimed ground, and primary sources now define it

The earlier report relied on vendor blogs for evidence handling. Primary sources now cover it. NIST IR 8387 says "It is best practice to hash digital images and other objects using a NIST approved hashing algorithm and the resulting hashes should be stored separately from the image or file". MD5 or SHA-1 are acceptable "if needed but newer algorithms are preferred". Verified copies make "best evidence" moot, because "the copy is identical to the original" ([NIST IR 8387](https://nvlpubs.nist.gov/nistpubs/ir/2022/NIST.IR.8387.pdf)). SWGDE's collection guidance says files "should be organized, verified (e.g., validating checksums) and protected from alteration", with "the date and time of transfer, as well as the location from which the files were collected", and ideally the device's make and model ([SWGDE 2021](https://www.swgde.org/wp-content/uploads/2023/11/2021-01-14-SWGDE-Guidelines-for-Video-Evidence-Canvassing-and-Collection_v1.0.pdf)). Its authentication guide asks examiners "Is the file a camera-original file?" and "Has the file been re-encoded?" It prefers a stream copy for derivatives and lossless formats for stills, and warns that "Video editing software may modify a file's metadata" ([SWGDE 2024](https://www.swgde.org/wp-content/uploads/2024/03/2024-03-07-SWGDE-Best-Practices-for-Digital-Video-Authentication-23-V-001-1.2.pdf)). The UK National Dash Cam Safety Portal needs only "a copy of the original file in unedited, uncompressed format", makes the submitter responsible for keeping the original, and says a wrong clock "is not an issue provided you refer to this in your statement". It also states that enhancement cannot recover a plate the recording failed to capture ([NDSP FAQ](https://nextbase.co.uk/ndsp-faq)). A text search for "hash", "MD5" and "SHA" in the BlackVue, Dashcam Viewer, Tesla, Thinkware and Nextbase documents found nothing, and none of the six products checked, Viofo included, describes any integrity data. That makes a hashed manifest unclaimed ground for DashLens. This is evidence of absence across six products, not proof.

DashLens's export today records the canvas with `MediaRecorder`, which re-encodes, and saves snapshots as JPEG. Both are fine as working copies, and both fall short of the SWGDE ideal. The premium version has five parts. "Export original files" makes byte-for-byte copies of the source clips. A clearly labelled "working copy (re-encoded)" holds the trimmed multi-camera clip with optional telemetry burned in. SHA-256 is computed in the browser for every original and every output. A manifest file, saved separately as NIST asks, lists file names, sizes, hashes, camera, recorded start and end, timezone, any user-noted clock offset, transfer time, source folder, camera model if known and the DashLens version. Evidence stills are saved as PNG. GPX/CSV is exported unsmoothed and labelled as raw. The summary records a known clock offset as a note rather than "fixing" the original. It offers no "enhance" option, and it makes no admissibility claim anywhere.

## Motion stays off the media clock and brief everywhere else

### Frequency decides whether anything animates

Emil Kowalski's blog states the rule DashLens needs: "never animate keyboard initiated actions. These actions are repeated sometimes hundreds of times a day". Remove animation from things "seen tens, maybe even hundreds of times a day" ([Kowalski, 7 Practical Animation Tips](https://emilkowal.ski/ui/7-practical-animation-tips); [Kowalski, Great Animations](https://emilkowal.ski/ui/great-animations)). His four-tier table ("100+ times/day… No animation. Ever.") and the line that a professional dashboard "should be crisp and fast" appear only in his GitHub skill file, not on the blog ([Kowalski STANDARDS.md](https://raw.githubusercontent.com/emilkowalski/skills/main/skills/review-animations/STANDARDS.md)). Apple's current HIG backs the rule. "In apps, generally avoid adding motion to UI interactions that occur frequently", "Let people cancel motion" and "Make motion optional" ([Apple HIG Motion](https://developer.apple.com/design/human-interface-guidelines/motion)). Rauno removed motion from his tool's core interactions after they "began to feel sluggish" and "suddenly felt like I was moving much faster". He notes that macOS context menus "appear without motion", fade out subtly, and blink the chosen item in the accent colour "to provide assurance" ([Rauno Freiberg](https://rauno.me/craft/interaction-design)).

In DashLens, play/pause, frame steps, seeks, number-key tile focus, the playhead, the map marker and the heading readout must track the media clock 1:1, drawn in the same frame as the canvas. The audit finds four violations in the current file. `#hArrow` still has `transition: transform .3s`, so the heading arrow trails the video by up to 300 ms and keeps swinging after a frame step. The load and export bars animate `width` instead of `transform: scaleX()`. `.chip` uses `transition: .15s` and `#toast` uses `transition: .2s`, the all-properties shorthand that Vercel bans with "Never transition: all" ([Vercel](https://vercel.com/design/guidelines)). The fourth is the reduced-motion rule. It sets `transition: none` and `animation: none` on every element, which removes the opacity fades that tell a user a menu opened or a toast appeared. Val Head's guidance is to swap movement for "an opacity fade or crossfade" and not to "unintentionally remove content or degrade the overall experience" ([Smashing](https://www.smashingmagazine.com/2020/09/design-reduced-motion-sensitivities/)). Emil's example does the same, turning a bounce into a fade ([Kowalski](https://emilkowal.ski/ui/great-animations)). Under reduced motion, DashLens should remove transform motion and keep 100–150 ms opacity fades.

### A token set built on numbers that survived verification

Two "standards" from the earlier token table did not survive. Material's "fade 150 ms in, 75 ms out" and "container transform 300/250 ms" figures are legacy M2-era values. They contradict the M3 duration tokens in the same file (Short1 50, Short2 100, Short3 150, Short4 200, Medium1 250, Medium2 300 ms and up) ([Material Motion.md](https://raw.githubusercontent.com/material-components/material-components-android/master/docs/theming/Motion.md); [androidx MotionTokens.kt](https://raw.githubusercontent.com/androidx/androidx/androidx-main/compose/material3/material3/src/commonMain/kotlin/androidx/compose/material3/tokens/MotionTokens.kt)). The exit-shorter-than-entrance rule now rests on NN/g: "a popup window may take 300ms to appear, but only 200 or 250ms to disappear". NN/g also gives "roughly 100 ms" for simple feedback, 200–300 ms for modals, and says "At 500ms, animations start to feel like a real drag" ([NN/g](https://www.nngroup.com/articles/animation-duration/)). Easing for exits is genuinely contested. Emil's blog says ease-in "is just not made for UI animations". NN/g's demo uses ease-in to exit, and M3 has accelerate curves for exits. Since exits are short, DashLens can use one strong ease-out for both, a choice rather than a consensus. Vercel's own production CSS uses stock Tailwind curves ([vercel.com](https://vercel.com)), and Emil notes that "The built-in easing curves in CSS are usually not strong enough" ([Kowalski](https://emilkowal.ski/ui/7-practical-animation-tips)). Apple recommends "starting with 100% damping, or no overshoot", with overshoot only when "the gesture… itself has momentum" ([Apple WWDC18](https://developer.apple.com/videos/play/wwdc2018/803/)). No DashLens interaction has momentum, so it needs no bounce.

Tooltips should use Radix's defaults: a **700 ms** first-show delay, then instant opening for neighbours within **300 ms** ([Radix](https://www.radix-ui.com/primitives/docs/components/tooltip)). They should never appear during a drag or scrub. Loading indicators need "a short show-delay (~150–300 ms) & a minimum visible time (~300–500 ms)", so fast local parses never flash a card ([Vercel](https://vercel.com/design/guidelines)). Responsiveness should meet web.dev's "good" Interaction to Next Paint of **200 ms or less at the 75th percentile** ([web.dev](https://web.dev/articles/inp)). That argues for parsing GPS and G-sensor data in a Worker. For long clip and event lists, use `content-visibility: auto` with `contain-intrinsic-size`, which cut rendering from 232 ms to 30 ms in web.dev's demo ([web.dev](https://web.dev/articles/content-visibility)). Emil's point about the main thread applies directly. The canvas timeline, map and chart redraw on `requestAnimationFrame`, so chrome motion should be CSS transitions on transform and opacity, which "remain smooth, no matter how busy the main thread is" ([Kowalski](https://emilkowal.ski/ui/great-animations)). DashLens should have no UI sounds, because they would mix with dashcam audio that may itself be evidence.

### Every state designed is what "a large team" means in practice

Scott Hurff's UI Stack gives every screen "up to five states": ideal, empty, error, partial and loading. It also splits empty into first use, "User-cleared data" and "No results" ([Scott Hurff](https://www.scotthurff.com/posts/why-your-user-interface-is-awkward-youre-ignoring-the-ui-stack/)). Vercel asks for "All states designed. Empty, sparse, dense, & error states" and layouts "Resilient to user-generated content" ([Vercel](https://vercel.com/design/guidelines)). Kosta Canatselis lists missing empty, loading and error states among the signs of AI-made design ([HEY](https://world.hey.com/kostac/spot-the-slop-a-ui-designer-s-guide-to-fixing-ai-defaults-4c448c9c)), so this is where a small project most visibly beats a generated one. The WAI-ARIA dialog pattern settles focus. "When a dialog closes, focus returns to the element that invoked the dialog", unless that element no longer exists. For destructive steps, "set focus on the least destructive action" ([WAI-ARIA APG](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/)). DESIGN.md covers errors, scans and missing telemetry. These states are still unnamed.

## DashLens matches a listed AI-default cluster, so identity has to come from the footage

### What the measurements actually say

The most-cited measurement now has a confirmed history. Adrian Krebs first scored **500** Show HN pages against **15** patterns: 21% heavy (5 or more patterns), 46% mild and 33% clean ([HN](https://news.ycombinator.com/item?id=47864393)). The current version of his post scores **1,590** pages against **16** patterns with new thresholds: 22% high (4 or more), 32% medium and 46% low ([Krebs](https://www.adriankrebs.ch/blog/design-slop/)). Both sets of numbers are real; they come from two versions of one post. Every check is "a deterministic CSS or DOM check", with an estimated 5–10% false-positive rate. The list of tells came from asking designer friends, so it is consensus, not data ([Krebs](https://www.adriankrebs.ch/blog/design-slop/)). The first version's rates show which tells are common. Gradients appeared on 28% of sites, untouched shadcn and centred hero titles on 23.5% each, perma-dark on 20.3%, icon-card grids on 20.1% and glass panels on 17.1%. The memorable pill badge above the title was rare, at 4.7% ([GIGAZINE](https://gigazine.net/gsc_news/en/20260423-design-slop/)). Krebs's perma-dark pattern is specific: "Perma dark mode with medium-grey body text and all-caps section labels". A dark background alone is not the pattern. His own verdict is mild: "Is this bad? Not really, just uninspired." Critics on Hacker News note that there is no pre-2023 baseline, that many tells come from Tailwind UI and shadcn, and that "Models have their own archetypes" that shift over time ([HN](https://news.ycombinator.com/item?id=47864393)). The earlier report attributed the "thresholds tuned on the same sample" critique to Krebs. It actually targets a June 2026 IOV Labs paper with 202 sites and 27 tells. The same review adds that "brand purple is not a tell, since Stripe uses it heavily and scores 0… what gives a page away is defaults with nothing deliberate next to them" ([maxiality](https://maxiality.com/how-to-spot-an-ai-generated-website/)).

The cause is the most agreed point in the literature. NN/g says AI tools produce "a similar, generic look" because they "favor common patterns from their training data and often default to component libraries like Shadcn". They default to "neutral, minimalistic visual aesthetics with bright color accents". NN/g adds, fairly, that this bias "could potentially be good for the user experience" ([NN/g](https://www.nngroup.com/articles/ai-prototyping/)). Anthropic calls it "Distributional convergence": without direction, the model "samples from this high-probability center". Banning one default moves it to the next, with Space Grotesk after Inter ([Anthropic](https://claude.com/resources/articles/improving-frontend-design-through-skills)). That is why the target moves. Anthropic's current frontend-design skill lists five clusters. Cluster 2 is "a near-black background with a single bright acid-green or vermilion accent". Cluster 5 is "template chrome": "a tracked-out ALL-CAPS eyebrow label above every heading; meta strings joined with middle dots ('A · B · C'); labels built as 'WORD — fragment'… tinted near-black (#0B0B0B, #111)… a monospace face for small data labels; a '→' appended to link and button text". The skill also says "fade-and-slide-up entrances on each section and hover transitions on every card… read as AI-generated", and that "All traits are legitimate for some briefs, but they are defaults rather than choices" ([Anthropic SKILL.md](https://raw.githubusercontent.com/anthropics/skills/main/skills/frontend-design/SKILL.md)). Jim Nielsen adds the 2026 look of "beige/cream colors, orange accents, and serif typefaces", the sparkle emoji, "shimmering text" for async work, and AI apps whose icons are "much smaller, thinner… than their native counterparts" ([Jim Nielsen](https://blog.jim-nielsen.com/2026/ai-aesthetic/)). Impeccable's catalogue now has **62 detector rules**. One reads "Purple gradients and bright cyan on dark backgrounds are familiar AI defaults". Another reads "Keep the dark theme if it suits the product, and reduce the glow so useful information stands out" ([Impeccable](https://impeccable.style/slop)).

### Where DashLens is exposed, and why it keeps its dark theme

Measured against these lists, DashLens touches more tells than the earlier report found. Its base is a tinted near-black (#0a0c0f) with one bright warm accent, close to Anthropic's cluster 2. It has **28 middle-dot joins** in UI strings, a cluster-5 item, although most of them separate real data ("0.42 g · firm"). Its bright cyan (#35c3d6) draws the heading arrow, the left-turn G axis and the route, which is Impeccable's "bright cyan on dark". The settings drawer pairs a 1 px border with a 30 px shadow, which Impeccable calls "Hairline border with wide shadow". The tile labels and info overlay use `backdrop-filter: blur(4px)`, which on panels would be glassmorphism. The info overlay sets labels and values alike in mono. Some things are clear. The file has no gradient glows, no emoji badges, no all-caps eyebrows and no "→" on buttons; its arrows mark ranges and menu paths. Its fonts, IBM Plex Sans and Mono embedded at 400–600, are not on Krebs's, Impeccable's or Anthropic's lists of overused faces.

Keeping the dark theme is right. Apple says that "In rare cases" an app "that supports immersive media viewing" can "use a permanently dark appearance that lets the UI recede and helps people focus on the media" ([Apple HIG](https://developer.apple.com/design/human-interface-guidelines/dark-mode)). A dashcam viewer is that rare case. Switching to whatever palette is fashionable would only move DashLens to the next default, as Anthropic warns. No source tests whether ordinary users, as opposed to designers and Hacker News readers, see dark plus one accent as AI-made. DashLens's first audience on GitHub and Hacker News is exactly the group that applies these heuristics, though.

### Counter-moves that read as authored

The published guidance agrees on method: "Spend your boldness in one place" ([Anthropic SKILL.md](https://raw.githubusercontent.com/anthropics/skills/main/skills/frontend-design/SKILL.md)), "Show the product… the fastest single change available", and make a claim "that could only be about you" ([21st.dev](https://21st.dev/blog/website-not-look-ai-generated)). Kosta Canatselis's definition is the test: "Slop is design with no author" ([HEY](https://world.hey.com/kostac/spot-the-slop-a-ui-designer-s-guide-to-fixing-ai-defaults-4c448c9c)). For DashLens, the one place for boldness is the **timeline**. It should have dense, honest ticks, event markers that differ in shape as well as colour, hatched and labelled gaps, telemetry lanes, and the amber playhead as the single brightest interactive mark. Everything else stays quiet. Orange becomes strictly semantic: the playhead, the selected event, the primary action and the focus ring, with no glow. The data colours need one audit under "one colour, one meaning". Braking leaves the danger red. The cyan drops in saturation and stops doubling as heading, route and left turn. Each G direction keeps its word label. The surfaces become real steps rather than one tinted near-black. Middle dots give way to layout in event rows and summaries, staying only where they separate two values. The drawer loses either its border or its wide shadow. The blur stays on tile labels over moving video, where it serves legibility, and goes nowhere else.

Icons and copy follow the same rule. foundey's analysis says "Lucide isn't the problem… The problem is that it ships its defaults untouched". It recommends a size scale and "One stroke weight… matched to your type weight" ([foundey](https://foundey.com/blog/ai-slop-icons)). Icons belong beside labels, not in tiles above headings, which is an Impeccable rule ([Impeccable](https://impeccable.style/slop)). A few custom glyphs for dashcam concepts (front and rear camera, parking event, impact) mark the product as authored. Copy should name concrete things in sentence case ("Drop the folder from your SD card", "Front and rear synced by clock time") and avoid "seamless", "unlock" and their kind, which The Admin Bar flags as suspicious ([The Admin Bar](https://theadminbar.com/how-to-edit-ai-website-copy/)). The em dash is contested. Writers defend it as "just language" ([Optimizely](https://www.optimizely.com/no/field-notes/articles/in-defense-of-the-em-dash-and-everything-else-on-this-ai-tell-trial)). The UI-specific tell is narrower: Anthropic's spaced "WORD — fragment" label. DashLens uses "—" only as the empty-value placeholder that DESIGN.md prescribes, and that use can stay. NN/g found that AI hero images carried no trust penalty when users did not know their origin ([NN/g](https://www.nngroup.com/articles/ai-generated-images/)). Real footage is still the product's own imagery. The README and any project page should show a real, consented dashcam frame with plates and faces blurred, a real track and a real G trace, never generated art.

## Conclusion

The verification pass sharpened the earlier thesis rather than overturning it. "Premium", "calm" and "not AI-made" are one property seen from three sides: evidence of an author who decided things about this product. The corrections all point the same way. APCA turned out stricter, so the greys must get lighter. The halo effect turned out to fade once people use the product, so usability carries more weight than polish. The motion standards turned out partly legacy, so frequency matters more than any duration table. Evidence handling now rests on NIST and SWGDE instead of vendor blogs, which makes the hashed-manifest export a defensible differentiator rather than a nice idea. The AI-slop numbers turned out to be one designer-sourced checklist in two versions, so the durable defence is domain specificity, not dodging a list.

Two findings change priorities. Tesla now ships a free, local, browser-based viewer with frame-synced telemetry, so DashLens's distinctiveness can no longer rest on "runs in the browser" or "private". It has to rest on multi-brand support, the timeline, the incident flow and evidence-grade export. And the cheapest premium gains are in the file already: one reduced-motion rule, one heading-arrow transition, 35 uses of an Lc 52 grey, 13 radii and a braking line drawn in danger red. Fixing those costs an afternoon and moves DashLens further from "generated" than any new palette could.
